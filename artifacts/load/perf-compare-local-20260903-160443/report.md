## 结论

- 本次测试中，两种版本都没有出现错误请求，错误率均为 `0%`。
- `admin_login`：
  - 吞吐几乎一致：`99.82` vs `99.83 rps`
  - 微服务平均响应略低：`179.10ms` vs `180.18ms`
  - 但差距极小，不能据此写“性能提升”
  - 微服务内存更高：`200.31MB` vs `172.62MB`
- `admin_users`：
  - 微服务吞吐略高：`297.70` vs `297.27 rps`
  - 微服务 P95 更低：`65.54ms` vs `66.98ms`
  - 但提升幅度都很小，仍不建议写“性能提升”
  - 微服务内存明显更高：`228.50MB` vs `189.38MB`
- `admin_logs`：
  - 微服务吞吐略高：`297.93` vs `297.63 rps`
  - 平均响应几乎相同：都约 `45.25ms`
  - 微服务 P95 略高：`63.74ms` vs `62.90ms`
  - 微服务 CPU 和内存都更高

## 差异解释

- `admin_login` 的主要开销是 BCrypt 密码校验，瓶颈在 CPU 而不在架构拆分，所以两边吞吐和延迟几乎一致。
- `admin_users` / `admin_logs` 都是轻量读接口，数据量很小，本地 H2 + 单 JVM 场景下，网络拆分开销几乎没有体现出来，因此两边性能非常接近。
- 微服务版本内存持续更高，主要因为：
  - 单独的 `user-service` 也要加载完整 Spring Boot 容器、依赖和连接池
  - 在本次对比里只有一个微服务进程承载相同能力，JVM 常驻开销更明显
- 微服务版本在部分接口 CPU 更低或更高，幅度都不大，说明当前场景下 CPU 差异主要来自 JVM 抖动、JIT 预热和瞬时线程调度，而不是架构层面的决定性差异。

## 是否可以写“性能提升”

- 不能直接写“微服务性能提升”。
- 因为本次三个接口的差距都非常小，没有形成稳定且明显的提升幅度。
- 更准确的表述应该是：
  - “在同机、同数据、同脚本、同并发条件下，微服务版与单体版整体性能接近；未观察到显著性能提升，但微服务版内存占用更高。”
