这十天做什么、做到什么程度、老师怎么检查

   10 天集中实践       前后两个阶段        项目 90 分        考勤 10 分


 先看这一句 这十天不是另做一个新系统。你们要接着上学期的小组项目做：先把原系统整理好并
 跑通自动构建，再把后端拆成微服务，最后用测试证明它还能正常工作。


一、这次实践要完成什么
实践分成前后两个阶段，两个阶段都要做。90 分项目成绩按小组统一评分，作为全组共享的基础分，
再根据每名成员的个人权重折算；10 分考勤按个人单独计算。

 • 前 5 天（40 分）：确认上学期的系统还能启动，补齐缺少的文档和测试，把前端、后端、数据
   库装进容器，并跑通 CI/CD。

 • 后 5 天（30 分）：把后端拆成至少 3 个业务微服务，自动部署到 Kubernetes，完成扩缩容、故障
   处理和性能对比。

 • 项目管理、交付、演示和答辩（20 分）：最后一天现场演示、答辩并提交全部材料。
 什么叫“补齐测试” 先看原项目已经有哪些测试、还缺哪些。缺的测试要补上，并在本机和流水线
 里实际跑通。不是多写几页测试文档，也不是只截一个“运行成功”的画面。


沿用上学期的项目
必须沿用上学期的小组和项目。第 1 天先把项目启动起来，列出完整的业务场景（用例）清单，并逐
项检查是否能正常使用。

 • 能正常启动：给当前版本打一个 Git 标签，建议命名为 monolith-start。这个版本不要再改，后面
   要用它和微服务版本做对比。

 • 启动不了：先修到能运行，再继续后面的任务。确实无法修复的，当天向教师或助教说明。
 为什么要保留这个版本 它就是你们改造前的原系统。验收时要证明：微服务版本完成了同样的主
 要业务，而且性能对比用的是同一套功能和数据。


二、所有业务场景（用例）都要完成，汇报时再选重点
第 1 天列出项目完整的业务场景（用例）清单，并由教师或助教确认。原项目中只有设想、尚未开发
的内容，第 1 天说明后确认是否计入。确认后的清单就是最终验收范围。清单中的每个用例都要能运
行，有对应的需求、设计、代码、测试和追溯记录。最终报告、答辩和现场演示可以从中选不少于 3
个有代表性的用例重点讲解，但其他用例也必须完成并接受检查。

3. 把系统装进容器并跑通 CI/CD
 • 前端、后端和数据库分别运行在容器中。数据库可以直接使用官方镜像，前端和后端要提交
   Dockerfile。
 • 准备数据库建表、数据迁移和测试数据脚本。换一台机器后，按 README 也能启动。
 • 向指定分支 push 一次代码后，流水线自动完成：取代码、安装依赖、编译、单元测试、集成测
   试、制作镜像、部署到 Kubernetes、健康检查。
 • 任何一步失败，后面的部署都不能继续。成功记录和失败记录都要保留。

 • 提交流水线配置、Kubernetes 部署文件、测试脚本和部署脚本。镜像要有版本号，不能只使用
   latest。
可以使用哪些工具 Jenkins、Gitea Actions、GitHub Actions、CodeArts、Gitee、云效等都可以。
Kubernetes 可以使用 Docker Desktop、Minikube、Kind 或 k3d。


四、后 5 天要做的事（30 分）

1. 把后端拆成至少 3 个业务微服务
这里数的是业务服务。API 网关、注册中心、配置中心、前端和数据库不算在 3 个业务微服务里。不
要按用例数量机械拆分，要说明每个服务负责什么业务、为什么这样分。

 • 每个服务能单独构建、测试和部署。
 • 每张业务表要明确归哪个服务管理。其他服务不能直接读写这张表。

 • 可以在同一个数据库服务器中使用不同数据库或 Schema，但不能跨服务直接联表查询。
 • 跨服务的数据操作通过接口、事件或消息完成，并说明调用失败时怎么处理。
举个例子 订单服务需要商品信息时，应调用商品服务接口，不能直接查询商品服务的数据库表。

需要提交：服务划分图、服务接口清单、数据表归属表、跨服务调用说明，以及改造前后的两个代码
版本。


2. 让微服务也能自动构建和部署
 • 代码提交后，相关微服务自动完成构建、测试、制作镜像和部署。
 • 所有后端公开接口都要有 API 测试，清单中的全部业务场景（用例）都要做端到端回归测试。
   最终报告可重点展示不少于 3 个代表性用例的结果。
 • 要能查看服务日志、健康检查、就绪检查和版本号，并现场说明一次部署失败是怎么查出来的。

4. 对比改造前后的性能
选择 2 到 3 个主要接口。单体版本和微服务版本使用同一台机器、同一批数据、同一份压力脚本，并
各运行至少 3 次。记录并发数、吞吐量、平均响应时间、P95 响应时间、错误率、CPU 和内存。

 不要求微服务一定更快 如果微服务版本更慢，也可以。把测试条件和原始结果交出来，并解释为
 什么会有差异。只有确实测出来的结果，才能写“性能提升”。


五、每天怎么管理项目

每日站会
每天上午 9:00 到机房后，各组开 5 分钟左右的站会。每个人只回答三件事：昨天做了什么、今天做什
么、现在卡在哪里。每天中午 12:00 前提交一份约 200 字的站会简报。云盘地址在课程群发布。


看板和任务
可使用 CodeArts、GitHub Projects、Gitee、云效、TAPD 或其他同类平台。教师和助教要能查看仓库和
项目看板。每项任务至少写清：

      字段                                  内容

任务内容             任务编号、名称、对应的需求或用例

谁来做              负责人，必要时写协作者

什么时候完成           计划时间、实际完成时间

做到什么算完成          验收条件

证据               对应的提交、Pull Request、测试或文档链接


 • 每天保存一次看板和统计页面截图，并写上日期。最终报告只放有代表性的任务截图，其他任务
     由教师在线查看。
 • 重要代码建议通过 Pull Request 合并，并由另一名组员检查。
 • Git 提交次数不能直接当作个人贡献大小。还要看任务难度、质量、测试、文档和协作。

先共享项目成绩，再按个人权重折算
 计算方法 个人项目成绩 = min(90，小组共享项目成绩 × 个人权重)；课程总成绩 = min(100，个人
 项目成绩 + 个人考勤成绩)。个人权重只作用于项目成绩；考勤按个人实际出勤单独计算，不共享、
 不加权。

 • 一般情况下，个人权重在 0.9 到 1.1 之间。经教师和助教核实，特殊情况可低至 0.5。组长不会因
   为是组长自动加权。
 • 全组权重之和不能超过组员人数。
 • 权重方案原则上由全员签字或线上确认。意见不一致时，先按 1.0 计算，再由教师和助教根据看
   板、提交、评审、站会和答辩情况决定。
