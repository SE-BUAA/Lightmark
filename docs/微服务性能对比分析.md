# 微服务 vs 单体性能对比分析(flights / hotel)

> 数据来源:服务器压测原始输出 `summary.csv`(与 `docs/技术总结报告.md` §5.2 配套)。
> 原始文件按仓库约定存放在 `artifacts/`(被 .gitignore 排除,不随 git 提交,本地与服务器各有归档副本)。

## 1. 测试条件

- 压测方式:同机、同数据源(同一 MySQL)、同一脚本、同一参数;ApacheBench 风格脚本 `scripts/loadtest/perf-compare.sh`
- 参数:并发 30、每轮 3000 请求、每接口每版本 3 轮
- 被测对象:
  - `mono`:单体版 `backend`(常驻进程,无资源限额)
  - `msa`:微服务版 product-service(k3s 单副本,CPU limit 500m,Hikari 默认连接池)
- 接口:`/api/flights/search`(机票搜索)、`/api/hotel/list`(酒店分页列表)

## 4. 观察与解读

1. **错误率均为 0**,两种形态都能在压力下正确完成请求,差异在吞吐与延迟而非正确性。
2. **微服务"平均快、p95 极长"**:avg 仅 13–25ms,但 p95 达 0.75–1.65s(p95/avg ≈ 60 倍),是典型的**排队型延迟**(请求等待连接池/线程空出),而非单个请求本身慢。
3. **单体轮间波动大**:flights 从 1772 到 6053 rps(3.4 倍),说明单体未打满、测量受 JVM 预热与机器噪声影响;hotel 三轮稳定在 ~6900 rps,更接近其真实能力。
4. **微服务轮间呈上升趋势**(flights 40→44→78;hotel 58→71→72),符合 JVM 预热、连接池建立后的渐稳特征。
5. **瓶颈不在数据库**:两者查同一 MySQL,单体同库可达数千 rps;微服务单副本的瓶颈在自身 CPU 限额与连接池。

## 5. 结论

- **单点性能**:微服务单副本(CPU limit 500m + 默认连接池)远低于无限额单体,差距约两个数量级。差异主要由**部署形态**(资源限额、独立 JVM、连接池过小、多一跳网关)主导,不能解读为"微服务架构本身慢 100 倍"。
- **价值定位**:微服务的收益不在单点吞吐,而在**横向扩展、故障隔离与独立发布**——配合 HPA 实验(1→2→4 副本,CPU 60% 阈值触发,3 万请求 0 失败),可通过加副本线性补回单点差距。
- **如实表述**(答辩口径):"同机同数据下,微服务单副本受资源限额与连接池限制,吞吐约为单体的 1/100;扩至多副本后整体吞吐随副本数上升,弹性扩缩容由 HPA 实验验证;单体在无限额单点场景下性能占优。"

## 6. 后续优化建议

1. Hikari `maximum-pool-size` 调至 ≥ 压测并发(如 40–60),消除连接池排队导致的 p95 长尾;
2. 适当上调资源限额(如 CPU 1 核)并复测,量化"限额 vs 架构"各自的贡献;
3. 保留启动探针后的预热期再计吞吐,减少 JIT 影响;
4. 增加"多副本聚合吞吐"一组的对比(当前为单副本数据),与 HPA 实验互相印证。

## 7. 局限

- CSV 未记录机器规格与采样细节,结论以**量级与趋势**为准;
- 仅覆盖 product-service 两个查询接口,不代表登录(BCrypt 型)、写接口的结论。
