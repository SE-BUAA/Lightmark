# 软件需求规格说明书

## 1 范围

### 1.1 标识

- **系统名称**：拾光旅行（Lightmark）一站式出行旅游平台
- **文档名称**：软件需求规格说明书（Software Requirements Specification）
- **版本号**：V1.0
- **项目标识**：Lightmark-SRS-2026
- **适用范围**：本文档适用于“拾光旅行”项目的需求分析、设计、开发及验收阶段，作为各阶段工作的需求依据。

### 1.2 系统概述

“拾光旅行”是一款集机票预订、酒店住宿、旅游度假、火车票购买、智能行程规划及社区分享于一体的综合型Web应用。系统采用B/S架构，响应式Web设计，支持PC端、平板和移动端浏览器访问。

系统涵盖六大核心模块：
- **主体框架与运营管理（M1）**：用户认证、权限管理、后台运营仪表盘、产品管理、订单干预、用户管理等。
- **用户中心与AI智能助手（M2）**：个人资料管理、出行人管理、积分会员体系、安全设置、AI智能客服、语音输入搜索、自然语言修改个人信息等。
- **机票预订模块（M3）**：多条件机票搜索、航班列表展示与排序筛选、价格日历与低价提醒、舱位选择与附加服务、乘客信息填写与下单、模拟支付与出票、订单详情与退改签，以及自然语言机票搜索、智能退改签解释等AI增强功能。
- **酒店预订模块（M4）**：酒店搜索、酒店列表与地图模式、多维度筛选、房型详情与价格、入住人下单、订单管理与发票申请、取消订单，以及酒店智能推荐对话、用户评论自动摘要等AI功能。
- **火车票+旅游度假模块（M5）**：火车票车次查询与坐席选择、乘客信息与儿童/学生票、订单支付与出票、改签与退票；度假产品搜索与详情预订、度假订单与合同生成，以及旅游产品智能文案生成、智能行程助手等AI功能。
- **智能行程与社区模块（M6）**：手动拖拽规划行程、行程共享与导出、出行前智能提醒、订单评价、游记发布与互动、问答社区、当地玩乐推荐，以及AI生成个性化行程、游记自动生成、评论情感分析与自动回复、智能问答机器人等AI功能。

系统前后端分离：前端基于Vue 3 + Vite + TypeScript，后端基于Spring Boot 3.5.x + MyBatis-Plus，数据库采用MySQL 8.0 + Redis，部署于Ubuntu服务器（2核2GB，58GB磁盘）。AI能力通过调用大模型API（如讯飞星火、百度ERNIE）实现，由后端统一代理。

## 3 需求

### 3.1 所需的状态和方式

系统应支持以下运行状态和方式：

| 状态/方式        | 描述                                                         |
| :--------------- | :----------------------------------------------------------- |
| **正常运行状态** | 系统在标准配置下持续提供服务，所有功能可用，响应时间满足性能指标。 |
| **维护状态**     | 系统进行计划内维护（如数据库备份、软件升级）时，可短暂下线或切换至维护页面，维护前向用户发布通知。 |
| **降级运行状态** | 当外部依赖（如大模型API）不可用或服务器资源紧张时，系统自动降级：AI功能返回预置Mock响应，非核心功能（如社区推荐）暂停，核心预订流程保持可用。 |
| **测试状态**     | 在测试环境中运行，使用模拟数据，不影响生产数据。             |

### 3.2 需求概述

#### 3.2.1 目标

- **开发意图与应用目标**：本系统旨在提供一个综合的在线火车购票和旅游服务平台，解决现有产品在用户体验、功能整合和操作便捷性方面的不足。系统将整合火车购票、酒店预订和火车餐购买，提供一站式服务，提高用户满意度和操作效率。*（注：根据项目实际扩展，系统已涵盖机票、酒店、火车票、度假、行程规划及社区等全场景）*

- **主要功能和流程**：包括用户注册登录、机票预订、酒店预订、火车票预订、度假产品预订、智能行程规划、社区互动（游记、问答、评价）、消息通知和支付功能。用户通过简洁的界面完成查询、预订、支付等操作，系统提供实时反馈和订单管理。

- **系统高层次图与关系**：该系统是一个独立产品，但设计上考虑与其他旅游服务产品如航班预订和景点预订系统的兼容性和整合可能性。系统架构图包括用户界面、服务处理层、数据管理层和外部接口（详见概要设计说明书）。

#### 3.2.2 运行环境

- **硬件环境**：服务器应支持高并发访问，确保稳定运行在云平台上。推荐配置：2核CPU、2GB内存、58GB磁盘。客户端无特定硬件要求，支持各种智能手机、平板和个人电脑。
- **支持环境**：需要MySQL 8.0数据库系统支持大数据量存储和快速查询，Redis 7.x用于缓存和会话管理。后端服务部署于Ubuntu 22.04 LTS服务器，前端支持主流浏览器（Chrome、Safari、Firefox最新版）。

#### 3.2.3 用户的特点

面向所有需要通过网络预订出行旅游产品和服务的用户。用户特点包括：需求高效率、高可用性的服务，常有即时的服务需求；对价格敏感，希望获得优惠和积分；部分用户需要行程规划和社区分享功能。从使用系统来说，要求使用导向简单易懂，有充足的引导，能使绝大多数人快速上手。管理员用户需要后台管理能力，进行产品上下架、订单干预和用户管理。

#### 3.2.4 关键点

**关键功能**（六大模块核心功能详见3.2.6功能需求详细描述）：

- **用户认证与权限**：注册/登录（手机号、邮箱），JWT鉴权，角色管理（普通用户、管理员）。
- **机票预订**：多条件搜索、航班列表、舱位选择、乘客信息填写、模拟支付、订单管理、退改签。
- **酒店预订**：目的地/日期搜索、地图模式、筛选排序、房型选择、预订、取消订单。
- **火车票预订**：车次查询、坐席选择、乘客信息、支付出票、改签退票。
- **度假产品**：跟团游/自由行搜索、详情预订、合同生成。
- **智能行程**：手动/AI生成行程、拖拽规划、导出分享、行前提醒。
- **社区互动**：游记发布（图文）、点赞评论收藏、问答社区、订单评价。
- **AI增强**：智能客服、自然语言搜索、智能推荐、评论摘要、情感分析、游记生成。
- **支付模拟**：微信/支付宝/积分抵扣模拟。
- **消息通知**：订单状态变更、支付结果、车次变更等通知（邮件/站内信）。

**关键技术和算法**

- Web开发技术：使用Vue 3框架进行前端开发，使用Spring Boot 3.5.x后端技术实现服务器端逻辑。
- 数据库技术：采用MySQL 8.0存储用户信息、订单信息等数据，MyBatis-Plus作为ORM框架。
- 搜索算法：机票/酒店/火车票的多条件查询与排序，使用数据库索引优化。
- 推荐算法：基于用户行为（浏览、收藏、购买）和热门产品的简单推荐（初期），后期可扩展为协同过滤。
- 价格日历算法：聚合未来30天最低票价，使用缓存提升性能。
- AI调用算法：封装大模型API调用，支持Prompt模板、重试机制和降级Mock。
- 支付模拟算法：实现简单的支付模拟功能，包括生成订单、模拟支付过程、积分抵扣计算。

#### 3.2.5 约束条件

- **开发期限与经费**：项目周期为15周（第4周至第15周），无实际经费，使用开源技术和免费云资源。
- **技术与方法**：使用敏捷开发模式（迭代增量），采用现有成熟技术和框架以缩短开发时间和降低成本。后端必须使用Java（Spring Boot），前端不限但本方案采用Vue 3。
- **法律与文化约束**：遵守相关数据保护法规和隐私政策，保护用户安全隐私性。用户密码需加密存储（BCrypt），敏感信息脱敏展示。
- **团队约束**：6人团队，每人至少负责4个模块，每个模块至少5个主要功能。

### 3.3 需求规格

#### 3.3.1 软件系统总体功能/对象结构

系统总体功能结构如下（详见概要设计说明书）：

### 3.4 CSCI能力需求

#### 3.4.1 火车票购票能力

- **能力描述**：能够处理用户的火车票查询、选择和购买。
- **输入要求**：用户输入查询参数（出发地、目的地、日期和时间）。
- **处理需求**：
  - 必须在2秒内返回搜索结果。
  - 能够显示至少100个搜索结果（不同车次和座位类型）。
  - 支持至少100并发用户进行票务查询。
- **输出要求**：显示车次信息，包括出发时间、到达时间、车程时长、座位类型及其价格。
- **性能参数**：
  - 响应时间：≤ 2 秒。
  - 吞吐率：至少1000个请求/分钟。
- **异常处理**：
  - 在无匹配车次情况下提供“无可用车次”提示。
  - 网络延迟或服务器问题时提供适当错误信息并尝试重新连接。
- **连续运行需求**：99.9% 的正常运行时间。

#### 3.4.2 酒店预订能力

- **能力描述**：实现酒店搜索、详情查看和预订功能。
- **输入要求**：用户输入目的地、入住日期和退房日期。
- **处理需求**：
  - 必须在3秒内返回搜索结果。
  - 支持按价格、评分进行结果排序。
  - 能够提供至少50家不同酒店的数据。
- **输出要求**：显示酒店名称、评分、位置、价格和房型可用性。
- **性能参数**：
  - 响应时间：≤ 3 秒。
  - 吞吐率：至少500个请求/分钟。
- **异常处理**：
  - 当无可用房间时提供“无房间可预订”提示。
  - 系统错误或服务中断时应有重试机制和用户通知。
- **连续运行需求**：99.8% 的正常运行时间。

#### 3.4.3 支付处理能力

- **能力描述**：安全地处理支付事务，支持多种支付方式（微信、支付宝、积分抵扣模拟）。
- **输入要求**：用户选择支付方式并输入支付详情（模拟环境不验证真实账户）。
- **处理需求**：
  - 必须在5秒内完成支付验证和处理。
  - 应对所有支付交易进行加密处理（模拟环境使用HTTPS）。
- **输出要求**：显示支付成功或失败的通知。
- **性能参数**：
  - 响应时间：≤ 5 秒。
  - 吞吐率：至少2000个支付事务/小时。
- **异常处理**：
  - 支付失败时提供错误原因和重新支付选项。
  - 在支付数据处理中保持数据一致性和恢复机制。
- **连续运行需求**：99.95% 的正常运行时间。

#### 3.4.4 消息通知能力

- **能力描述**：向用户发送实时通知，包括订单确认、取消和重要信息更新。
- **输入要求**：系统生成的事件触发消息发送。
- **处理需求**：
  - 必须确保所有重要通知在1分钟内送达。
  - 支持Email通知和站内信。
- **输出要求**：用户收到清晰准确的消息内容。
- **性能参数**：
  - 响应时间：≤ 60 秒。
  - 吞吐率：至少1000条消息/小时。
- **异常处理**：在消息发送失败时进行重试，并记录异常原因。

#### 3.4.5 AI服务能力

- **能力描述**：提供AI智能客服、自然语言搜索、智能推荐、行程生成等能力。
- **输入要求**：用户输入自然语言文本或选择功能触发。
- **处理需求**：
  - AI响应时间≤10秒（含大模型API调用）。
  - 支持降级：API不可用时返回预设Mock响应。
- **输出要求**：返回清晰、有用的AI生成内容。
- **性能参数**：吞吐率至少100个请求/小时（受限于免费API限额）。
- **异常处理**：API超时或失败时自动重试1次，仍失败则返回Mock响应并记录日志。

### 3.8 适应性需求

系统应能够适应以下变化：

- **业务规则变化**：退改签手续费规则、积分抵扣比例、会员等级阈值等应通过配置文件或数据库参数管理，支持动态调整而不需重新部署。
- **数据量增长**：当产品数据、订单数据超过百万级时，数据库应支持分页查询、索引优化，必要时可引入分表策略。
- **并发量增长**：系统设计支持水平扩展，可通过增加后端实例配合Nginx负载均衡提升吞吐量。
- **新接入第三方服务**：AI模块、地图模块应保持接口抽象，便于替换不同供应商的API。
- **多端适配**：前端响应式设计应适应不同分辨率设备，后续可封装为移动端App（通过WebView）。

### 3.9 保密性需求

- **用户密码**：必须使用BCrypt算法单向哈希加密存储，禁止明文存储。
- **用户敏感信息**：身份证号、手机号在数据库存储时可考虑加密（本项目模拟环境暂不强制，但在日志打印和前端展示时需脱敏：手机号显示`139****1234`，身份证号显示`410101**********X`）。
- **JWT令牌**：使用安全的密钥签名，令牌有效期设置为7天，支持刷新。
- **HTTPS**：生产环境必须启用HTTPS，使用Let's Encrypt免费证书。
- **SQL注入防护**：使用MyBatis-Plus预编译语句，禁止字符串拼接SQL。
- **XSS防护**：前端输出时转义HTML特殊字符，后端对用户输入进行过滤。

### 3.10 保密性和私密性需求

- **数据访问控制**：普通用户只能访问自己的订单和个人信息，管理员可访问全部数据但操作需记录日志。
- **隐私政策**：在用户注册时展示隐私政策，明确告知数据收集和使用范围。
- **账号注销**：用户申请注销后，系统应在7天内删除或匿名化其个人信息（本项目模拟注销操作，实际仅标记为删除状态）。
- **日志脱敏**：系统日志中不得记录明文密码、完整身份证号等敏感信息。
- **第三方数据共享**：不主动向第三方共享用户数据，大模型API调用时不发送用户真实身份信息。

### 3.13 软件质量因素

- **功能性**：CSCI应能够实现合同中所要求的全部功能，并满足用户的需求。这包括对功能的完整性和正确性的要求。
- **可靠性**：CSCI应能够产生正确、一致的结果，即使在异常情况下也应该具有恢复能力，保证系统的稳定性和可靠性。
- **可维护性**：CSCI的代码结构应该清晰，易于理解和修改，以便于进行后续的维护和更新。
- **可用性**：CSCI应该能够在需要时进行访问和操作，保证系统的可用性，降低用户因系统不可用而造成的损失。
- **灵活性**：CSCI应该具有一定的灵活性，能够适应需求变化，快速响应用户的需求，并支持系统的扩展和升级。
- **可移植性**：CSCI应该易于修改以适应新的环境，可以在不同的硬件平台或操作系统上进行部署。
- **可重用性**：CSCI的组件应该设计成可重用的，可以被多个应用使用，提高系统的开发效率和代码的复用性。
- **可测试性**：CSCI应该易于进行充分的测试，包括单元测试、集成测试和系统测试等，以确保软件的质量和稳定性。
- **易用性**：CSCI应该易于学习和使用，用户界面设计应该友好，操作流程应该简单明了，以提升用户的满意度和使用体验。

### 3.14 设计和实现的约束

- **技术栈约束**：后端必须使用Java（Spring Boot），前端使用Vue 3，数据库使用MySQL。不得引入额外的商业软件或依赖。
- **编码规范**：后端遵循阿里巴巴Java开发手册，前端遵循Vue官方风格指南。使用Lombok简化POJO，使用ESLint + Prettier统一前端代码风格。
- **文档约束**：所有API必须提供Swagger注解，生成在线文档。数据库表结构变更需同步更新《数据库设计》文档。
- **安全约束**：所有用户输入必须经过校验和过滤，所有数据库操作必须使用预编译或参数化查询。
- **部署约束**：系统必须能在2核2GB服务器上正常运行，不得因资源不足导致频繁OOM。
- **时间约束**：项目必须在第十五周周日之前完成所有交付。

### 3.15 数据

本节描述系统处理的主要数据及其特征（详见3.7节和《数据库设计》文档）。数据按业务模块划分为：用户数据、产品数据、订单数据、社区数据、行程数据、配置数据。数据量预估：用户数≤1000（演示），产品数≤100，订单数≤500，游记数≤200，整体数据库规模<500MB。

数据生命周期：
- 用户数据：注册时创建，注销时标记删除。
- 订单数据：创建后保留，支付成功后不可删除，取消订单保留记录。
- 产品数据：由管理员上下架，下架产品不删除但不可预订。
- 日志数据：保留30天，超过自动清理。

### 3.16 操作

系统常规操作包括：
- **用户操作**：注册、登录、搜索产品、查看详情、下单、支付、查看订单、取消订单、评价、发布游记、评论、提问、规划行程等。
- **管理员操作**：登录后台、查看仪表盘、上/下架产品、调整价格/库存、查看所有订单、手动取消/退款、封禁/解封用户、调整会员等级。
- **系统自动操作**：订单支付超时自动取消（15分钟）、定期清理过期日志、数据库自动备份。

操作流程详见各模块时序图（详细设计说明书）。

### 3.17 故障处理

| 故障类型         | 处理方式                                                     |
| :--------------- | :----------------------------------------------------------- |
| 数据库连接失败   | 后端重试3次，间隔2秒，仍失败则返回503错误，并记录日志        |
| 大模型API超时    | 重试1次，超时返回预置Mock响应，不阻塞主流程                  |
| Redis连接失败    | 降级为不使用缓存，直接查询数据库                             |
| 服务器内存不足   | JVM配置`-Xmx512m`，超出时触发OOM后自动重启（使用systemd或supervisor） |
| 订单支付超时     | 定时任务每5分钟扫描待支付订单，超过15分钟自动取消并释放库存  |
| 并发冲突（超卖） | 使用数据库乐观锁（版本号）或悲观锁（select for update）保证库存扣减原子性 |
| 前端API请求失败  | axios拦截器统一提示，并提供重试按钮                          |

### 3.18 算法说明

| 算法                         | 说明                                                         |
| :--------------------------- | :----------------------------------------------------------- |
| **火车/机票搜索算法**        | 根据出发地、目的地、日期在数据库中进行索引查询。使用复合索引`(departure, arrival, date)`提升性能。往返查询则执行两次单程查询后合并。 |
| **价格日历算法**             | 对于给定产品（如航班），查询未来30天每天的最低票价。使用Redis缓存结果，缓存时间1小时。若缓存未命中，执行SQL聚合查询`SELECT date, MIN(price) FROM schedules WHERE ... GROUP BY date`。 |
| **酒店推荐算法（简单）**     | 根据用户搜索条件（目的地、日期、人数）返回酒店列表，支持按价格、评分排序。AI智能推荐模块通过调用大模型解析用户自然语言需求后，转化为结构化筛选条件执行查询。 |
| **积分抵扣算法**             | 用户下单时可选择使用积分抵扣，抵扣规则：100积分=1元，单笔订单最多抵扣订单金额的30%。计算实付金额 = 总金额 - min(积分余额, 总金额*0.3*100)/100。 |
| **退改签手续费计算（模拟）** | 机票：起飞前24小时以上退票扣10%，24小时内扣50%；火车票：开车前15天以上免费，48小时以上扣5%，24-48小时扣10%，24小时内扣20%。度假产品：根据取消政策（免费取消/部分退款/不可退款）计算。 |
| **AI调用降级算法**           | 调用大模型API时设置超时10秒，失败后自动重试1次。若仍失败，根据调用类型返回预设的Mock模板（如客服回复模板、行程模板）。 |

## 6 尚未解决的问题

- **模拟收费的具体实现方式应该如何实现**：本项目采用模拟支付，无需对接真实支付网关。拟实现方案：前端展示支付方式选择（微信/支付宝/积分），后端生成支付记录，设置“模拟支付”按钮，点击后直接更新订单状态为“已支付”，并生成虚拟交易流水号。积分抵扣需在订单创建时计算。
- **大量火车批次信息应当如何获得，以什么样的形式存储在数据库中**：由于无法获得真实实时数据，采用预置模拟数据方式。根据主流线路（如京沪线、京广线等）手动生成约50条车次记录，存储在`product`表中（`product_type='TRAIN'`），具体时刻、座位信息存储在`extra` JSON字段中。演示时足够使用。
- **航班、酒店、度假产品数据来源**：同样采用预置模拟数据，从公开API或手动构造约50个航班、30家酒店、20个度假产品。
- **AI大模型API免费额度限制**：使用讯飞星火或百度ERNIE的免费额度，若超出限制或调用不稳定，后端实现Mock响应模式，确保演示时AI功能仍可展示。
- **高德地图API的调用**：仅用于酒店地图模式演示，若申请key困难，可使用静态地图图片或模拟位置标记代替。
