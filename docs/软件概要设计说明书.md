### 1.1 编写目的

本文档旨在提供“拾光旅行（Timemark）”一站式出行旅游平台的概要设计，明确系统的整体架构、模块划分、核心接口及数据库设计。本文档为后续详细设计和开发工作提供技术蓝图与指导依据。预期读者包括项目开发人员、测试人员、项目管理人员及课程评审教师。

### 1.2 背景

开发软件系统名称：拾光旅行（Timemark）一站式出行旅游平台。 任务提出者：软件工程课设。 开发者：贾宇翔，汤斯杰，王得明，赵静怡，胡天灏，李子恒 运行该软件的计算站（中心）：网页端。

本文中使用的专门术语和外文首字母组词的原词组的意义如下：

- **拾光旅行**：集机票、酒店、火车票、度假产品预订、智能行程规划及社区分享于一体的综合型Web应用。

## 2 系统需求概述

### 2.1 需求规定

- **输入项目**：用户的注册/登录信息、产品搜索条件（日期、目的地等）、订单信息、评价与游记内容、AI自然语言指令。
- **输出项目**：机票/酒店/火车票列表、订单详情及状态、推荐内容、AI生成的行程与回复。
- **功能性能要求**：系统应能支撑核心预订流程的稳定运行，首页加载时间控制在2秒内，核心接口响应时间低于3秒，保证99%的核心流程成功率。

### 2.2 业务目标

实现一站式旅游出行服务，覆盖从“灵感获取-预订支付-行中服务-游后分享”的全场景。核心目标包括：在线机票/酒店/火车票/度假产品预订、智能行程规划、社区分享与AI辅助功能，提供便捷、智能化的旅游服务体验。

### 2.3 运行环境

#### 2.3.1 设备

- **计算机设备**：用户可通过台式机或笔记本电脑的现代浏览器（Chrome, Edge等）访问系统Web端。
- **移动设备**：用户可通过智能手机或平板电脑的浏览器访问响应式Web应用，支持iOS和Android系统，界面自适应不同屏幕尺寸。

#### 2.3.2 支持软件

- **操作系统**：服务器使用Ubuntu 22.04 LTS；客户端支持Windows, macOS, iOS, Android。
- **Web服务器**：使用Nginx进行反向代理和静态资源托管。
- **数据库系统**：采用MySQL 8.0关系型数据库。
- **编程语言与框架**：后端使用Java (JDK 17) 及Spring Boot 3.5.x框架；前端使用Vue 3 + Vite + TypeScript。

### 2.4 设计约束

- **隐私性**：用户密码必须使用BCrypt加密存储，敏感信息（身份证、手机号）在展示和日志中脱敏。
- **操作方便性**：界面设计需简洁直观，符合主流OTA平台用户习惯。
- **技术约束**：后端必须使用Java（Spring Boot），前端不限，本方案采用Vue 3。
- **资源约束**：最终部署服务器配置为2核CPU、2GB内存，需在此限制下保证系统稳定。
- **时间约束**：所有开发与交付活动必须按计划在第15周前完成。

### 2.6 非功能需求

#### **2.6.1 性能稳定性**

1. **响应时间****指标：**所有核心业务接口的平均响应时间应低于 3 秒。
2. **并发处理能力：**系统需在至少 100 个并发用户同时访问的压力测试环境下，保持逻辑处理无误且响应耗时无显著抖动。
3. **事务成功率：**确保机票、火车票及酒店预订等核心交易流程的成功率不低于 99%。

#### **2.6.2 安全性要求**

1. **身份认证：**全站采用 JSON Web Token实现无状态身份认证，确保前后端分离架构下的接口调用安全。
2. **数据加密存储：**用户登录密码必须使用 BCrypt 哈希算法进行加密。用户隐私数据（如身份证号、联系电话）在数据库中必须使用 AES-256 对称加密标准进行加密存储。
3. **传输安全：**生产环境强制开启 SSL 连接，确保 Web 流量与数据库交互链路的安全性。

**2.6.3 可扩展性与维护性**

1. **模块化设计：**遵循 M1~M6 模块化划分，确保各业务组件高度解耦，便于后续 AI 增强功能的迭代更新。
2. **数据处理：**采用逻辑删除模式，确保用户数据的可追溯性与隐私合规性。

**2.6.4 易用性**

1. **界面交互：**采用响应式布局，保证在不同分辨率的网页端均能正常显示。
2. **操作逻辑：**核心预订流程路径需简洁明确，从搜索到提交订单的步骤应尽可能精简，以提升用户体验。

## 3 系统接口设计

### 3.1 接口设计

#### 3.1.1 用户接口

##### 命令和语法结构

**火车购票功能**：

- 用户可以使用命令进行火车购票操作，命令示例：选择购买火车票界面，选择时间为2024-05-01，起始站北京，终点站上海
- 回答信息包括：可选的火车车次列表，每个车次的座位类型和价格，示例：以下是您可选择的车次：K123（动车）- 座位类型：二等座、价格：300元；T456（普通火车）- 座位类型：硬座、价格：150元

**酒店预订功能**：

- 用户可以使用命令进行酒店预订操作，命令示例：进入预订酒店界面，选择目的地为上海
- 回答信息包括：当地推荐的酒店列表和相关信息，示例：以下是您可选择的酒店：如家酒店- 价格：400元/晚，评分：4.5星

**火车餐购买功能**：

- 用户可以使用命令进行火车餐购买操作，命令示例：进入订餐界面，选择火车车次K123，选择用餐时间为午餐
- 回答信息包括：可选的餐品列表和价格，示例：以下是您可选择的餐品：鸡肉饭- 价格：50元，牛肉面- 价格：40元

**订单查询和取消功能**：

- 用户可以使用命令查询历史订单，命令示例：查询个人订单
- 回答信息包括：用户的历史订单列表，示例：以下是您的历史订单：订单号：2024001，内容：K123二等座2024-05-01，总金额：300元

用户可以通过支持网络连接的设备（如电脑、智能手机等）访问“汪汪旅途”系统，使用网页或移动应用程序进行操作。硬件控制面板包括用户界面（UI）元素，例如输入框、按钮、下拉菜单等，用于与系统进行交互。

#### 3.1.2 与其他软件、硬件接口

##### 软件与硬件接口安排

- **数据库接口**：系统与数据库之间的接口用于存储和检索用户信息、火车车次、酒店信息、订单数据等。
- **支付接口**：系统需要与支付平台接口，用于处理用户的缴费操作，包括火车票购买、酒店预订、餐品订购等支付流程。
- **消息通知接口**：系统需要与消息服务接口，用于向用户发送订单状态变更、订购结果等通知消息。
- **火车信息接口**：系统需要与火车信息查询接口，用于获取火车车次信息，包括座位类型和价格等。

##### 系统元素间接口安排

- **用户模块与订单模块的接口**：用户模块通过用户ID关联订单模块，用于查询和管理用户的订单信息。
- **火车购票模块与支付模块的接口**：火车购票模块通过订单ID关联支付模块，用于处理火车票购买的支付流程。
- **酒店预订模块与支付模块的接口**：酒店预订模块通过订单ID关联支付模块，用于处理酒店预订的支付流程。
- **火车餐购买模块与支付模块的接口**：火车餐购买模块通过订单ID关联支付模块，用于处理火车餐购买的支付流程。

### 3.2.2 物理结构设计要点

本节从数据库落地角度说明数据的存储方式、访问方法、存取单位和索引关系。

| 设计项       | 设计内容                                                     | 重点说明                                             |
| ------------ | ------------------------------------------------------------ | ---------------------------------------------------- |
| 存储要求     | 数据库采用 `MySQL 8.0`，库名为 `lightmark`，字符集为 `utf8mb4`，排序规则为 `utf8mb4_unicode_ci`，存储引擎为 `InnoDB` | 支持事务、行级锁、外键约束，适合订单类业务           |
| 字段类型要求 | 金额字段采用 `DECIMAL(10,2)` 或 `DECIMAL(12,2)`，状态字段采用 `TINYINT` 或 `VARCHAR` 枚举编码，时间字段采用 `DATETIME`，长文本采用 `TEXT`，可变结构采用 `JSON` | 兼顾精度、可扩展性和结构表达能力                     |
| 访问方法     | 后端通过 `Controller + Service + Mapper` 三层结构访问数据，`Mapper` 层采用 `MyBatis-Plus BaseMapper`，复杂查询使用 `XML` 或注解 SQL | 统一访问规范，兼顾开发效率与复杂查询能力             |
| 存储单位     | 单条记录为基本单位；订单详情以 `orders + order_item + payment_record` 为组合单位；产品详情以 `product + 扩展表` 为组合单位；行程详情以 `travel_plan + travel_plan_item` 为组合单位 | 既支持精细更新，也支持组合查询                       |
| 索引关系     | 主键索引、唯一索引、业务查询索引、联合索引并行设计           | 重点面向登录、搜索、订单查询、社区查询等高频场景优化 |
| 事务与一致性 | 订单创建、支付、退款、库存扣减等操作需在同一事务中完成       | 保证金额、库存、订单状态一致                         |
| 热冷数据策略 | 核心交易数据长期保留；图片等大文件只存地址；高频可重建数据可缓存到 `Redis`；订单与支付数据定期备份 | 兼顾性能、成本和数据安全                             |

## 4 系统数据库设计

### 4.1 数据库选择

系统采用 **MySQL** **8.0** 作为关系型数据库管理系统。MySQL 具有以下优势：

- **稳定可靠**：开源、成熟，支持 ACID 事务，适合订单、支付等对数据一致性要求高的业务。
- **性能优异**：支持索引优化、查询缓存，可满足旅游平台的高并发查询需求。
- **扩展性强**：支持 JSON 字段类型，便于存储产品扩展属性（如航班额外信息、酒店房型配置等）。
- **生态完善**：与 Spring Boot + MyBatis-Plus 无缝集成，开发效率高。

数据库部署于 Ubuntu 服务器（2核2G），使用 **InnoDB** 存储引擎以支持事务和外键约束。

### 4.3 数据库关系设计

系统核心实体间的关系如下：

- **用户 (user)** 与 **订单 (orders)**：一对多。一个用户可下多个订单，一个订单仅属于一个用户。  外键：`orders.user_id` → `user.id`
- **用户 (user)** 与 **常用出行人 (traveler)**：一对多。一个用户可添加多位出行人。  外键：`traveler.user_id` → `user.id`
- **用户 (user)** 与 **游记 (post)**：一对多。一个用户可发布多篇游记。  外键：`post.user_id` → `user.id`
- **用户 (user)** 与 **评价 (review)**：一对多。一个用户可对多个订单进行评价。  外键：`review.user_id` → `user.id`
- **用户 (user)** 与 **行程规划 (travel_plan)**：一对多。一个用户可创建多个行程计划。  外键：`travel_plan.user_id` → `user.id`
- **产品 (product)** 与 **订单 (orders)**：一对多（通过订单明细关联）。一个产品（如航班）可被多个订单购买。  实际关联通过 `flight_order_detail.product_id` → `product.id` 实现。
- **产品 (product)** 与 **酒店房型 (room_type)**：一对多。一个酒店产品可包含多个房型。  外键：`room_type.hotel_id` → `product.id`（仅当 `product_type=HOTEL`）
- **订单 (orders)** 与 **支付记录 (payment_record)**：一对一。一个订单对应一条支付记录。  外键：`payment_record.order_id` → `orders.id`
- **游记 (post)** 与 **评论 (comment)**：一对多。一篇游记可有多条评论。  外键：`comment.target_id` → `post.id`（且 `target_type='POST'`）
- **评价 (review)** 与 **评论 (comment)**：一对多。一条评价可有多条回复评论。  外键：`comment.target_id` → `review.id`（且 `target_type='REVIEW'`）

### 4.5 数据库安全性考虑

1. **访问控制**  
   1. 数据库账号 `se` 仅授予所需的最小权限（SELECT, INSERT, UPDATE, DELETE），禁止使用 root 账号。  
   2. 应用程序通过配置独立的数据库连接池，密码加密存储（如 Jasypt）。  
   3. 生产环境数据库服务器仅允许后端应用服务器 IP 访问，禁止公网直接连接。
2. **数据加密**  
   1. 用户密码使用 **BCrypt** 哈希加密存储，不可逆。  
   2. 敏感字段（如身份证号 `id_card`、手机号 `phone`）在传输和存储时采用 AES 对称加密。  
   3. 支付记录中的 `transaction_id` 作为模拟数据，无需真实加密，但日志中避免打印完整信息。
3. **审计与备份**  
   1. `admin_log` 表记录所有管理员关键操作（产品上下架、订单干预、用户封禁等），便于追溯。  
   2. 定时全量备份 + 增量 binlog 备份。  
   3. 定期演练数据恢复流程，确保灾难可恢复。
4. **SQL** **注入防护**  
   1. 后端使用 MyBatis-Plus 预编译查询（`#{}` 占位符），严禁拼接 SQL 字符串。  
   2. 动态表名或字段名需使用白名单校验。
5. **隐私合规**  
   1. 逻辑删除标记 `deleted` 而非物理删除，保证用户注销后可恢复。  
   2. 用户注销时，根据隐私政策选择是否匿名化或物理清除个人数据。
6. **SSL** **连接**  
   1. 数据库连接强制使用 SSL（`useSSL=true`），防止中间人攻击。  
   2. 开发环境可临时关闭（`useSSL=false`），生产环境必须开启。

## 5 运行设计

### 5.1 运行模块组合

本系统采用前后端分离架构，各模块在运行期通过统一的 RESTful API 接口进行协同交互，具体运行模块组合如下：

- **表现层与交互模块**：基于 Vue 3 框架构建，负责向普通用户与管理员呈现响应式 Web 界面。该模块承载了从灵感获取、产品查询（机票/酒店/火车票）、智能行程规划到社区互动的全场景前端交互链路，实时响应用户的点击、滑动及表单输入。
- **核心业务逻辑模块**：依托后端的 Spring Boot 框架运行，是系统的控制中枢。负责处理高复杂度的业务流转，包括但不限于：多产品形态的库存校验、动态价格与手续费计算阶梯、AI 自然语言指令解析与内容生成，以及完整的订单生命周期管理。
- **数据访问与持久化模块**：作为业务逻辑层与 MySQL 8.0 数据库交互的桥梁。该模块负责高效、安全地执行用户画像、航班/车次/酒店资源、订单流水及社区图文等海量数据的 CRUD 操作，并利用数据库索引与事务机制保证核心交易数据的一致性与完整性。
- **支付与交易流转模块**：作为独立的业务单元处理资金流向，涵盖模拟微信/支付宝网关请求、积分抵扣核算、支付状态轮询与异步回调验证。
- **异步消息与通知模块**：用于解耦非核心链路，在订单状态发生关键节点变更（如出票成功、超时取消、退票审核通过）或社区内发生高价值互动时，系统异步触发消息服务，向用户发送实时通知。

### 5.2 运行控制

为保障系统在复杂业务场景及高并发请求下的健壮性，系统在运行期实施以下严格控制：

- **用户会话与状态流转控制**：基于 JWT (JSON Web Token) 实现无状态的身份认证与权限拦截。对核心交易链路（如：产品搜索 -> 详情查看 -> 订单填写 -> 支付确认）实施严格的漏斗式状态校验，防止越权访问、重复提交或跳过必填步骤的非法请求。
- **高并发与库存事务控制**：针对节假日购票、促销抢房等高频并发场景，系统设计需保证在 100 级别模拟并发下的核心交易链路稳定不崩溃。通过底层数据库的行级锁（悲观锁/乐观锁机制）或应用层缓存扣减，彻底杜绝票源/客房超卖及订单状态冲突现象。
- **全局异常捕获与****容错机制**：建立后端的全局异常处理中心，对网络超时、服务不可用、业务规则冲突（如余额不足、商品下架）进行精准捕获。确保系统在遇到不可预见错误时，能够向前端返回标准化的错误状态码与直观友好的提示说明，同时后台记录详细的运行时日志以供追踪排查。

### 5.3 运行时间

结合本平台“高频查询、稳定交易”的业务特性，系统对关键运行节点的时间指标作出如下强制规范：

- **前端加载与交互****响应时间**：严格控制 Web 端的页面渲染效率，首页静态资源与核心数据流的初始加载时间必须控制在 2 秒以内。前端界面的组件切换、表单字段校验需达到毫秒级响应，保证操作顺滑无卡顿。
- **核心接口数据处理时间**：对于机票多维条件筛选、酒店地图房型查询及 AI 行程生成等重量级读写操作，依托合理的数据库索引与代码逻辑优化，核心接口的端到端响应时间必须严格控制在 3 秒以下。
