# 开发规范 v2.0（软件工程基础实践·微服务阶段）

## 一、版本控制规范（Git）

### 1.1 分支模型（核心）

```text
develop（部署/集成分支——只收合并，不做开发）
   ▲ 发版：merge 后 push → 触发完整 CI/CD（测试→镜像→K8s 部署→健康检查）
   │
msa-develop（日常开发分支——开发主战场）
   ▲ 功能完成 → 手动 merge 回 msa-develop
   │
test/<feature>（功能分支：从 msa-develop 切出，命名 test/<feature>）
```

| 分支 | 用途 | push 是否触发部署流水线 |
| --- | --- | --- |
| `develop` | 集成/发布，只接受 merge | ✅ 触发（workflow 仅监听 develop） |
| `msa-develop` | 团队日常开发，直接小步提交 | ❌ 不触发 |
| `test/<feature>` | 功能/修复分支 | ❌ 不触发 |

> `main` 保留为历史/稳定标签分支（`monolith-start` 等），不做日常使用。

**典型流程（一个功能）**

```bash
git checkout msa-develop && git pull
git checkout -b test/<feature>            # 1. 从 msa-develop 切功能分支
# 开发、本地测试，小步提交
git push origin test/<feature>            # 2. 推送（不触发部署）
# 自查，重要改动请他人 review
git checkout msa-develop && git pull
git merge test/<feature>                  # 3. 手动 merge（同上学期习惯）
git push origin msa-develop
# 需要发版/部署时：
git checkout develop && git pull
git merge msa-develop && git push origin develop   # 4. 触发 CI/CD 自动部署
```

**分支命名**：`test/<feature>`，英文小写、连字符，例如 `test/order-refund-fix`、`test/user-service`。

### 1.2 提交信息格式（Conventional Commits）

```text
<type>(<scope>): <中文描述>
```

**type**：`feat`（新功能）/ `fix`（修复）/ `docs`（文档）/ `test`（测试）/ `perf`（性能）/ `refactor`（重构）/ `style`（格式）/ `chore`（构建工具）。

要求：

- 一次提交只做一件事；
- 描述具体（如 `fix: 订单退款金额计算错误`），不要用"update""修改"等模糊词；
- 涉及数据库/接口/公共模块的改动，body 里写明影响。

### 1.3 文件与提交原则

- 所有源码、配置、测试、文档必须由 Git 跟踪并随提交推送；禁止只在服务器上改文件；
- 临时文件（日志、本地环境配置、IDE 元数据）加入 `.gitignore`；
- 提交前检查 `git status`，**严禁把 `.env` / `server.env` / `deploy/certs/` 提交进仓库**（已 gitignore，误提交按 §8 处理）。

## 二、后端开发规范（Spring Boot）

### 2.1 包结构与命名

单体（`backend/`，冻结对照用）：

```text
top.ortus.lightmark.backend
├── controller / service / dao / dto / config
├── common（ApiResponse 等）/ exception / security / utils / converter
```

微服务（`msa/<svc>-service/`，第二阶段）：

```text
msa/
├── pom.xml                # 父 POM（公共依赖、版本管理）
├── lightmark-common/      # 公共模块：ApiResponse、JwtTokenService、异常、工具
├── user-service/          # 独立 pom + src + test
├── product-service/
├── order-service/
└── content-service/
```

- 每服务只依赖 `lightmark-common`，**禁止依赖其他 service 模块**；
- 文件名大驼峰（PascalCase），每个 Controller/Service/DAO/DTO 独立 `.java` 文件。

### 2.2 分层与代码风格

- **Controller**：只做参数校验、调用 Service、返回统一响应，不写业务逻辑；
- **Service**：业务逻辑与事务，定义接口便于测试替换；
- **DAO**：数据访问，遵循"每张表唯一归属一个服务"；
- 使用 Lombok 减少样板代码；方法参数过多时封装 DTO；
- API 统一返回 `ApiResponse<T>`（`code=0` 成功）；业务异常抛 `ApiException(code, msg)`，全局异常处理兜底。

### 2.3 配置管理

- 敏感信息（DB 密码、AI Key、JWT 密钥）一律环境变量注入，禁止硬编码；
- 每服务独立配置：数据库指向自己的 schema（`lightmark_<域>`）；
- 配置项按模块分组并注释。

### 2.4 AI 功能约定

- AI 相关接口放 `controller/ai` 包；调用封装在 Service，Controller 只做转换；
- 每个 AI 调用必须配置超时；记录耗时与 prompt（注意隐私脱敏）；
- AI 服务不可用时返回降级提示（如"AI 服务繁忙"），不直接抛错。

## 三、前端开发规范（Vue 3 + TypeScript）

### 3.1 目录结构

```text
src/
├── api/           # 按域封装的 API（auth.ts / user.ts / flight.ts / hotel.ts / train.ts / vacation.ts / community.ts）
├── components/    # 公共组件（含 auth/ ai/ 等子目录）
├── composables/   # 组合式函数（use*.ts）
├── router/        # 路由（含 admin 子路由）
├── stores/        # Pinia（auth.ts / train.ts 等）
├── views/         # 页面（auth/ admin/ hotel/ module/ ...）
├── types/         # TS 类型定义
└── utils/         # 工具（request.ts 统一请求封装）
```

### 3.2 规则

- 每个组件/API 模块/Store/组合式函数独立文件；组件大驼峰、API 小驼峰、组合式函数 `use` 开头；
- 使用组合式 API（`<script setup lang="ts">`）；样式 `scoped`；
- 所有请求走 `utils/request.ts`（统一 baseURL、token、错误提示），不散落 axios 调用；
- Pinia 按模块划分，状态修改走 actions；
- 路由守卫 `router.beforeEach` 按 roles 控制，需登录页面 `meta: { requiresAuth: true }`，管理页 `adminOnly`。

## 四、数据库规范

### 4.1 表归属与 Schema

- 每张业务表**唯一归属**一个服务（见 `docs/微服务拆分方案.md` §4 数据表归属表）；
- 每服务独立 schema：`lightmark_user / lightmark_product / lightmark_order / lightmark_content`；
- **禁止跨服务直接查表/联表**，跨服务数据一律走接口（internal API）；
- 同一 MySQL 服务器、不同 schema，不跨服务联表查询。

### 4.2 迁移管理（Flyway）

- 每服务独立 Flyway（`db/migration/<svc>/*.sql`）；
- 迁移文件命名 `V<yyyyMMdd>__<描述>.sql`；
- **已发布的迁移文件禁止修改**，结构变更一律新增迁移；
- 禁止直接在服务器上执行 ALTER 而不更新迁移脚本；
- 表结构变更同步更新 `docs/数据库设计.md`。

## 五、微服务开发规范（第二阶段核心）

1. **服务边界**：按业务域划分（user/product/order/content），理由见拆分方案；不按用例数量机械拆；
2. **独立构建测试部署**：每个服务能 `mvn -pl <svc> -am test` 单独测试、单独打包、单独部署；
3. **跨服务调用**：走 `internal` 接口（`/internal/...`），必须实现失败处理：
   - 超时（默认 3s）+ 重试（1 次）+ 熔断（Resilience4j）+ 降级返回；
   - 次要操作（积分等）用异步补偿（outbox + 定时重试），达到最终一致；
4. **数据一致性**：下单等主链路用本地事务；**不使用分布式事务**，答辩说明取舍；
5. **镜像版本**：每服务独立 tag `<svc>-1.0.<run_number>` + `sha-<commit>`，**不用 latest 部署**；
6. **可观测性**：每服务保留 `/api/health`；能看日志、健康检查、就绪检查、版本号。

## 六、CI/CD 规范

- **触发**：仅 `develop` push 触发完整流水线（取代码→装依赖→编译→单元测试→集成测试→制作镜像→部署 K8s→健康检查）；`msa-develop` / `test/*` push 不触发；
- **门禁**：任何一步失败，后续部署立即停止；成功/失败记录保留（Actions 历史 + 服务器 `deploy-history.log`）；
- **测试**：`mvn test`（单元+集成）+ 前端构建全绿才允许构建镜像；测试报告归档；
- **镜像**：版本号见 §5.5；推送 GHCR；
- **部署**：复用 `scripts/deploy-k8s.sh`（按服务 apply → rollout → 健康检查，失败自动回滚上一次成功版本）；
- 提交流水线配置、K8s 部署文件、测试脚本、部署脚本到仓库。

## 七、测试规范

| 类型 | 要求 |
| --- | --- |
| 单元测试 | 关键类/方法/业务规则/异常分支；必须有断言 |
| 集成/API 测试 | 模块间调用、数据库访问、对外接口；主/备/异常流程都覆盖 |
| 端到端测试 | 从接口入口走完完整业务用例；覆盖用例清单全部场景 |

- 测试失败即流水线失败（不发布、不部署）；
- 新功能必须带测试；测试报告写清总数/通过/失败/原因/环境；
- 本地提交前：后端 `./mvnw test`，前端 `npm run build`。

## 八、安全红线（课程明确要求）

- ❌ 仓库中**严禁出现**：密码、Token、数据库口令、云平台密钥、`.env` / `server.env` / 证书私钥；
- 一律用 GitHub Secrets / k8s Secret / 环境变量管理；
- 误提交密钥：立即 `git rm --cached` 移除、更换该密钥，并告知全组；
- review 时互相检查密钥泄漏。

## 九、文档与协作

- 功能改动同步更新对应 `docs/` 与追溯表编号（`REQ/UC/…/TC` 保持一致）；
- 看板任务：编号+名称+负责人+时间+验收条件+证据链接（PR/测试/文档），每天截图存档；
- 每日站会三件事（昨天做了什么/今天做什么/卡在哪），简报 200 字内当天提交；
- **重要改动（数据库、跨服务接口、公共模块）必须他人 review**；普通功能自查后手动 merge；
- 提交与 PR 是个人权重（0.9–1.1）的客观证据，认真记录。

## 十、合并与回滚

- 合并冲突：先在功能分支内 `git merge msa-develop` 解决，再合回；
- 误推 develop：`git revert`（保留历史），避免强推；
- 代码找回：`git reflog` / `monolith-start` 标签 / 远端分支。
