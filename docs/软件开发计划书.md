# 软件开发计划书

## 1 引言

#### 1.1 标识
- **系统名称**：拾光旅行（Lightmark）一站式出行旅游平台
- **文档名称**：软件开发计划书（Software Development Plan）
- **版本号**：V1.0
- **适用范围**：本文档适用于“拾光旅行”项目开发的全生命周期，作为项目管理、进度把控及资源分配的核心基准。

#### 1.2 系统概述
“拾光旅行”是一款集机票预订、酒店住宿、旅游度假、火车票购买、智能行程规划及社区分享于一体的综合型Web应用。系统采用响应式Web设计，前后端分离。前端基于Vue 3与Vite，后端基于Spring Boot 3.5.x与MySQL 8.0。
项目不仅涵盖了传统在线旅游平台的核心电商交易链路，还创新性地引入了基于大语言模型的通用AI能力，如智能行程规划、评论情感分析、AI游记生成与智能客服等，致力于为现代旅行者提供从“灵感获取-预订支付-行中服务-游后分享”的智能化全场景服务。

#### 1.3 文档概述
本文档是“拾光旅行”项目开发过程中的指导性文件。全文详细规定了项目的交付产品、进度安排、资源需求、风险管理策略以及整体软件开发活动的实施计划。其主要目的在于为开发团队、项目经理以及作为“模拟甲方”的授课教师/助教提供明确的项目全景图，确保项目按时、保质完成。

#### 1.4 与其他计划之间的关系
本文档是本项目的主控计划，其他阶段性文档将以此为基础展开：
1. **《需求规格说明书》**：对本文档中第4章的工作概述进行详细的业务与功能层面的展开。
2. **《概要/详细设计说明书》**：受本文档规定的技术选型和总体进度约束，将需求转化为具体的技术蓝图。
3. **《测试计划与报告》**：依附于本文档制定的迭代周期与验收标准进行。

#### 1.5 基线
- **需求基线**：在第8周周日提交《软件需求规格说明书》并通过评审后确立，此后的任何核心需求变更需经全组讨论并提交变更记录。
- **设计基线**：在第12周周日提交《软件详细设计说明书》后确立，冻结核心数据库表结构（如`orders`、`user`等核心表）与主要API接口定义。

## 3 交付产品

### 3.1 程序

本项目交付的可执行软件产品为“拾光旅行”一站式出行旅游平台，包含以下子系统（模块）：
#### 3.1.1 主体框架与运营管理子系统（M1）

- 用户认证与权限管理（注册/登录/JWT）
- 全局响应式前端框架
- 超级管理员仪表盘（交易额、订单量、热门目的地、用户增长曲线）
- 后台产品管理（上/下架航班、酒店、火车、度假产品，调价调库存）
- 后台订单总览与干预（手动取消/退款）
- 后台用户管理（封禁/解封、调整会员等级）

#### 3.1.2 用户中心与AI智能助手子系统（M2）

- 个人资料管理（头像、昵称、出行人）
- 积分会员体系（积分获取/抵扣、等级权益）
- 安全设置（修改密码、换绑手机号、注销）
- 我的订单聚合（多类型订单按状态分类）
- AI智能客服（大模型对话，回答常见问题）
- 语音输入搜索（语音转文字填充搜索框）
- 自然语言修改个人信息（如“把昵称改成小李”）

#### 3.1.3 机票预订模块（M3）

- 多条件机票搜索（单程/往返/多程）
- 航班列表展示与排序筛选
- 价格日历与低价提醒（订阅推送）
- 舱位选择与附加服务（行李额、保险、选座）
- 乘客信息填写与下单（15分钟支付）
- 模拟支付与出票（微信/支付宝/积分抵扣）
- 订单详情与退改签（手续费计算）
- 自然语言机票搜索（AI解析用户输入）
- 智能退改签解释（AI生成通俗说明）

#### 3.1.4 酒店预订模块（M4）

- 酒店搜索（目的地/日期/人数）
- 酒店列表与地图模式（高德地图模拟）
- 多维度筛选（星级、设施、取消政策）
- 房型详情与价格展示
- 填写入住人与下单（积分抵扣）
- 订单管理与发票申请（电子发票模拟）
- 取消订单（按政策计算退款）
- 酒店智能推荐对话（AI根据描述推荐）
- 用户评论自动摘要（AI生成优缺点总结）

#### 3.1.5 火车票+旅游度假模块（M5）

- 火车票车次查询与筛选（高铁/动车/普速）
- 坐席选择与选座/选铺
- 乘客信息与儿童/学生票（模拟）
- 火车票订单支付与出票（电子客票）
- 火车票改签与退票（阶梯手续费）
- 度假产品搜索（跟团/自由行/当地玩乐）
- 度假产品详情与预订（游客信息、PDF合同模拟）
- 旅游产品智能文案生成（AI生成亮点）
- 智能行程助手（结合度假提供天气、穿衣建议）

#### 3.1.6 智能行程与社区模块（M6）

- 手动拖拽规划行程（地图标注、调整顺序）
- 行程共享与导出（链接、PDF/图片）
- 出行前智能提醒（推送天气、路况）
- 订单评价（打分、文字、图片）
- 游记发布与互动（点赞、评论、收藏）
- 问答社区（提问/回答）
- 当地玩乐推荐（基于目的地）
- AI生成个性化行程（自然语言描述，输出完整行程）
- 游记自动生成（照片+关键词→图文草稿）
- 评论情感分析与自动回复（差评安抚）
- 智能问答机器人（社区提问AI自动回答）

>以上程序均以Web应用形式交付，部署于Ubuntu服务器，前端为响应式Vue 3单页应用，后端为Spring Boot REST API，数据库为MySQL 8.0。不包含移动端原生App，但支持手机浏览器访问。

## 4 所需工作概述

### 4.1 系统和软件的需求与约束

#### 4.1.1 需求

**功能需求**：
- 实现六大模块（M1～M6）共58项功能点
- 核心功能包括：用户注册登录、机票/酒店/火车票/度假产品预订、订单管理、积分会员、智能行程规划、社区评价。
- AI增强功能（智能客服、自然语言搜索、行程规划等）作为加分项，至少实现1～2项。

**用户需求**：
- 界面友好、操作流畅，符合主流OTA平台（携程、同程）的使用习惯。
- 支持PC端和移动端浏览器自适应，无需安装客户端。
- 用户数据（手机号、身份证号、密码）需加密存储，保证隐私。

**非功能性需求**：
- 性能：首页加载<2秒，搜索响应<3秒（模拟100并发）。
- 可用性：核心流程成功率≥99%。
- 安全性：JWT认证，BCrypt加密，防SQL注入，HTTPS（可选）。
- 可扩展性：模块低耦合，便于后续接入真实API。

#### 4.1.2 约束

- **时间约束**：必须按课程规定的截止日期提交各阶段文档及最终项目，不得延期。
- **技术约束**：后端必须使用Java（Spring Boot），前端不限。本方案采用Java（JDK 17 + Spring Boot 3.5.13）。
- **团队约束**：每组6人，每人至少负责4个模块，每个模块至少5个主要功能。
- **资源约束**：服务器为2核2GB内存、60GB磁盘的Ubuntu实例，数据库MySQL 8.0，需在此配置下正常运行。
- **质量约束**：不得直接抄袭开源项目或往届作品，引用须注明来源；使用大模型生成的代码需人工审查并提交说明文件。

## 5 实施整个软件开发活动的计划

#### 5.1 软件开发过程
结合课程大作业的时间紧迫性与需求的多样性，本项目采用带有明确里程碑的敏捷迭代开发过程（Scrum结合增量模型）。
- **阶段划分**：需求分析期（W1-W5） $\rightarrow$ 架构与设计期（W5-W8） $\rightarrow$ 增量迭代开发期（W8-W12） $\rightarrow$ 集成测试与交付期（W12-W15）。
- **迭代策略**：将6大模块（M1~M6）拆分为4个双周迭代。每个迭代都会产出一个可独立运行或演示的子系统增量。优先跑通最小可行性产品，即M1与M3/M4/M5的搜索与下单主流程。AI功能与复杂社区互动放在靠后的迭代进行。

#### 5.2 软件开发总体状态

##### 5.2.1 软件开发方法
1. **协作模式**：采用敏捷Scrum框架。队长兼任Scrum Master，定期召开线上站会跟进进度，使用任务看板管理开发流。
2. **分支管理模型**：采用简化版 Git Flow。设定 `main` 为保护主分支，各开发人员基于模块拉取 `feature/M1-auth` 等功能分支，完成后通过 Pull Request 合并，必须经过至少一人的 Code Review。
3. **API 优先原则**：前后端分离开发中，后端需优先输出 Swagger/Postman 接口文档，前端依据文档构建 Mock 数据进行视图开发，最后进行真实接口联调。

##### 5.2.2 软件产品标准
1. **代码规范**：
   - **前端**：遵循 Vue 官方风格指南，使用 ESLint + Prettier 统一格式化。注释符合 JSDoc 标准。
   - **后端**：遵循开发手册，变量命名严格采用驼峰式，数据库字段采用下划线命名。使用 JavaDoc 规范注释实体类与核心业务逻辑。
2. **文档规范**：所有过程文档均使用 Markdown 编写，版本号统一化，图表需保持清晰并附带文字说明。
3. **交付标准**：各模块至少覆盖《大作业要求》中规定的5个核心功能，无 P0 级（系统崩溃、核心链路阻断）Bug，并满足响应式适配要求。

##### 5.2.3 可重用的软件产品
1. **第三方依赖**：充分利用成熟开源生态。前端引入 Element Plus（后台管理）、ECharts（数据可视化）、Axios；后端引入 MyBatis-Plus（简化SQL编写）、Hutool（常用工具类集成）。
2. **内部资产沉淀**：
   - **M1 公共组件库**：封装全局通用弹窗、确认框、统一错误处理拦截器，供 M2-M6 直接复用。
   - **通用 AI 工具类**：后端封装统一的大模型调用服务（`AIClient.java`）和 Prompt 模板引擎，使得“行程生成”、“客服问答”、“评论摘要”等功能可以复用底层网络层。

##### 5.2.4 处理关键性请求
1. **安全性（Security）保证**：
   - 全局 API 采用 JWT 鉴权与拦截器路由守卫。
   - 数据库密码字段（如 `user.password`）必须使用 BCrypt 算法单向哈希加密存储。
   - MyBatis-Plus 底层采用预编译 SQL 防止 SQL 注入；前端实施严格的输入校验，防 XSS 攻击。
2. **稳定性与容灾保证**：
   - 针对外部 AI 接口可能出现的超时或不可用情况，设计降级策略。当大模型 API 响应超时，系统能自动返回预设的 Mock 文本，确保答辩演示的连贯性。
3. **规范合规保证**：
   - 模拟真实生产环境的隐私保护，所有敏感信息（如用户身份证、联系方式）在日志打印和管理后台展示时进行脱敏处理。

##### 5.2.5 计算机硬件资源利用
鉴于服务器资源有限（2核 2GB，58GB磁盘）：
1. **内存管控**：在服务器启动脚本中严格限制 JVM 堆内存（`-Xms512m -Xmx512m`），防止因并发导致的 OOM 宕机。
2. **性能优化**：数据库查询尽量命中索引，避免全表扫描；Nginx 开启 Gzip 压缩，静态资源前端压缩后再上传，降低带宽和磁盘压力。

##### 5.2.6 记录原理
所有项目决策必须记录在项目仓库的 Issue 或 README的变更日志中，确保团队信息同步，并为期末答辩和开发文档提供追溯依据。

##### 5.2.7 需方评审途径
本项目的需方主要为课程教师及助教。我们将在以下节点配合评审：
1. **文档节点评审**：按照课程规定的第7、8、10、12周节点，准时提交过程文档接受评阅，并根据反馈及时修改。
2. **最终验收展示**：准备详尽的演示PPT、文档，在答辩时直观展示开发成果。

#### 6.3.1 用户输入分析
- 普通用户输入包括注册登录信息、出行人信息、搜索筛选条件、下单支付信息、评价内容、游记图文、问答内容以及自然语言 AI 指令。

#### 6.3.2 运行概念
- 系统面向 PC 与移动端浏览器运行，采用前后端分离架构提供一站式旅游出行服务。
- 典型运行链路为：用户进入平台 -> 搜索与浏览产品 -> 下单与订单管理 -> 出行前提醒 -> 行中辅助 -> 出行后评价/游记/问答互动。
- 管理端独立负责产品管理、订单干预、用户管理和统计展示。
- AI 能力以辅助和增强为主，不影响核心交易链路的可用性，必要时允许以 Mock 或预置结果降级展示。

#### 6.3.3 系统需求
- 功能需求以《需求划分文档》中 M1~M6 六大模块为准，覆盖主体框架、用户中心、机票、酒店、火车票与度假、智能行程与社区等 58 个核心及扩展功能点。
- 非功能需求重点包括：首页加载时间控制在 2 秒左右、搜索响应时间控制在 3 秒以内、核心主流程成功率不低于 99%、支持响应式适配、敏感数据加密存储。
- 约束需求包括：必须在课程规定时间内完成；后端使用 Java 技术栈；服务器资源受限；AI 功能需具备可解释的降级策略。

### 6.4 系统设计

#### 6.4.1 系统设计决策
- 在终端形态上，选择响应式 Web 作为唯一交付形态，避免多端并行开发带来的成本膨胀。
- 在技术架构上，选择 Vue 3 + Spring Boot 3.5.x + MySQL 8.0 的前后端分离方案，以兼顾课程要求、团队熟悉度和后续扩展性。
- 在业务组织上，采用 M1~M6 模块化设计，保证多人并行开发和后续维护的清晰边界。
- 在外部依赖上，地图、AI、对象存储等第三方能力均通过适配层封装，降低耦合度，便于替换或降级。
- 在性能与稳定性上，坚持核心链路优先、AI 增强功能后置、部署资源按 2 核 2GB 环境进行保守设计。

#### 6.4.2 系统体系结构设计
- 整体结构分为表现层、业务层、数据层与外部服务接入层。
- 表现层由 Vue 3 页面、公共组件、路由守卫和状态管理组成，负责页面展示、输入校验和交互流程。
- 业务层由 Spring Boot 的 Controller、Service、Mapper、AI 工具类和统一异常处理构成，负责业务编排、权限控制和外部 API 调用。
- 数据层由 MySQL 表结构、索引、事务控制和必要的缓存组成，负责订单、用户、产品、社区内容等数据持久化。
- 外部服务层包括大模型 API、地图服务和对象存储服务，统一通过后端适配接口接入。

### 6.6 软件设计

#### 6.6.1 CSCI级设计决策
- 前端应用、后端服务、数据库脚本、部署配置被定义为主要软件配置项；M1~M6 作为业务设计分项贯穿需求、实现和测试全过程。
- 前端采用按业务模块划分页面与 API 的组织方式，后端采用按“控制器 - 服务 - 数据访问 - 实体/DTO”分层的结构。
- 公共能力优先抽取，包括统一登录态、统一返回体、统一异常处理、统一图片上传、统一 AI 调用入口等，减少重复开发。
- 订单、产品、用户、社区等核心领域对象优先标准化建模，确保后续跨模块复用。

#### 6.6.2 系统体系结构设计
- 前端通过路由划分首页、机票、酒店、火车票、度假、行程、社区、用户中心、后台管理等页面，并以公共布局和公共组件实现统一视觉与交互。
- 后端通过 RESTful API 暴露能力，核心模块包括用户认证服务、产品服务、订单服务、社区服务、AI 服务与后台管理服务。
- 数据库按领域对象组织，核心表包括 `user`、`traveler`、`points_log`、`product`、`room_type`、`orders`、`payment_record`、`flight_order_detail`、`travel_plan`、`post`、`comment`、`review`、`question`、`admin_log` 等。
- AI 能力通过 `AIClient` 与提示词模板统一接入，为智能客服、自然语言搜索、行程规划、游记生成和评论情感分析提供支撑。

#### 6.6.3 CSCI详细设计
- M1 详细设计重点为用户认证流程、权限拦截、后台 CRUD 通用页面和统计仪表盘数据接口。
- M2 详细设计重点为用户资料、出行人、积分与订单聚合模型，以及通用 AI 对话/输入处理流程。
- M3、M4、M5 详细设计重点为搜索条件对象、产品详情对象、订单状态流转、支付与取消/退改规则。
- M6 详细设计重点为 `travel_plan` 行程数据结构、游记与评论内容结构、问答对象模型、评价与社区互动关系，以及 AI 生成内容的保存与展示流程。
- 部署设计重点为静态资源目录、JAR 运行目录、数据库初始化脚本、环境配置文件与 Nginx 转发规则。

#### 6.7.3 配置项测试执行
- 单元级测试重点验证工具类、校验逻辑、状态转换逻辑和 AI 适配层。
- 接口级测试重点验证参数校验、权限控制、业务返回码、异常分支和数据库一致性。
- 页面级测试重点验证响应式布局、关键交互流程、表单校验、错误提示和图片上传展示。
- 对 M6 模块重点验证行程拖拽编辑、导出分享、评论互动、游记发布与 AI 生成结果落库展示。

#### 6.7.4 修改和再测试
- 缺陷按严重程度划分为 P0、P1、P2、P3 四级；P0/P1 缺陷必须在当前迭代闭环。
- 修复后由提交人完成自测，由 QA 或非原作者成员进行回归验证，验证通过后关闭缺陷。
- 对涉及公共组件、订单链路、权限控制和部署配置的修复必须增加回归检查范围。

#### 6.7.5 配置项测试结果分析与记录
- 每轮测试后输出阶段性测试记录，统计已测功能、通过率、遗留缺陷数和回归结果。
- 测试结论作为下一轮迭代或集成测试的准入依据；若核心链路未通过，不进入下一阶段。

### 6.8 配置项集成和测试

#### 6.8.1 配置项集成和测试准备
- 先完成 API 文档和前端 Mock 数据准备，再进行真实接口联调。
- 制定集成清单，明确前端页面、后端接口、数据库表和第三方服务之间的映射关系。
- 预先准备登录态、商品数据、订单数据、评价数据和 AI 预置回复，降低集成期阻塞。

#### 6.8.2 配置项集成和测试执行
- 按“认证与权限 -> 搜索与展示 -> 下单与支付 -> 订单管理 -> 社区与行程 -> AI 增强”的顺序集成。
- 重点打通跨模块业务链路，例如常用出行人复用到机票/火车票下单、订单数据复用到评价与游记发布、目的地信息复用到行程规划与当地玩乐推荐。
- 对外部服务集成重点验证 AI 超时、地图接口不可用、图片资源异常等场景下的降级处理。

#### 6.8.3 修改和再测试
- 集成缺陷由对应模块负责人和相关协作人共同修复，禁止单方修改公共接口而不通知关联成员。
- 每次集成修复后均执行冒烟测试，必要时补做端到端回归。

#### 6.8.4 配置项集成和测试结果分析与记录
- 记录各轮联调的通过场景、失败场景、问题归属、修复耗时和遗留风险。
- 集成测试结论作为进入合格性测试和系统测试的依据。

### 6.9 CSCI合格性测试

#### 6.9.1 CSCI合格性测试的独立性
- CSCI 合格性测试由 QA 成员组织实施，模块开发者不得单独判定本模块最终通过。
- 对关键模块尽量由未参与该模块编码的成员进行交叉验证，提高独立性。

#### 6.9.2 在目标计算机系统（或模拟的环境）上测试
- 合格性测试在 Ubuntu 服务器部署环境或与之等价的模拟环境上进行。
- 同时验证 PC 浏览器和移动端浏览器访问效果，确保响应式页面可用。

#### 6.9.3 CSCI合格性测试准备
- 依据需求划分文档和第3.5节验收标准，编制模块级合格性测试用例。
- 准备覆盖正常、边界和异常场景的测试数据，确保每个模块至少有一条完整演示链路。
- 对 AI 功能额外准备接口异常时的回退数据和演示脚本。

#### 6.9.4 CSCI合格性测试演练
- 在正式测试前进行一次内部演练，检查环境、数据、脚本、账号和依赖服务是否就绪。
- 演练重点发现环境问题、接口变更遗漏和示例数据不一致问题。

#### 6.9.5 CSCI合格性测试执行
- 逐模块验证功能点是否满足既定需求，重点检查 M1 的鉴权与后台、M3/M4/M5 的交易主链路、M6 的行程与社区核心流程。
- 对 AI 增强项在“可用”“可降级”“可解释”三个层面进行确认。

#### 6.9.6 修改和再测试
- 合格性测试发现的问题按缺陷流程跟踪，修复后必须回归至通过状态。
- 若模块合格性测试连续失败，项目经理有权调整范围或冻结低优先级功能。

#### 6.9.7 CSCI合格性测试结果分析与记录
- 输出模块级合格性测试结论，记录通过项、限制项、遗留项及其对最终答辩的影响。
- 结论文档纳入《测试报告》附件。

### 6.10 CSCI/HWCI集成和测试

#### 6.10.1 CSCI/HWCI集成和测试准备
- 本项目虽无专门硬件产品，但需验证软件配置项与目标计算机环境、网络环境、浏览器环境之间的协同工作。
- 准备服务器配置、域名/SSL、JAR 包、静态资源、数据库、日志目录和启动脚本。

#### 6.10.2 CSCI/HWCI集成和测试执行
- 验证 Nginx 反向代理、前端静态资源访问、后端接口访问、数据库连接、文件上传路径和日志输出是否正常。
- 验证在 2 核 2GB 服务器下系统能稳定启动并完成核心流程操作。
- 验证目标浏览器、不同分辨率和校园网络条件下的访问效果。

#### 6.10.3 修改和再测试
- 对服务器参数、Nginx 配置、数据库连接池、静态资源压缩和 JVM 启动参数进行调优后再验证。
- 若出现环境相关问题，优先修复部署配置和脚本，而非修改业务逻辑绕过问题。

#### 6.10.4 CSCI/HWCI集成和测试结果分析与记录
- 记录部署成功时间、资源占用、访问延迟、典型问题和优化措施。
- 输出服务器部署验证结论，为最终验收提供依据。

### 6.11 系统合格性测试

#### 6.11.1 系统合格性测试的独立性
- 系统合格性测试由 QA 牵头，全体成员配合，尽量由非功能直接开发者承担演示与验证角色。
- 在课程条件允许时，以教师/助教意见作为外部验收参考。

#### 6.11.2 在目标计算机系统（或模拟的环境）上测试
- 系统合格性测试在最终部署服务器和真实浏览器环境上执行，必要时同步准备本地备用演示环境。
- 对现场网络不可控的情况，提前准备关键页面截图、录屏和本地应急演示方案。

#### 6.11.3 系统合格性测试准备
- 依据第3.5节验收标准编制系统级测试清单，覆盖六大模块核心功能、主要 AI 能力、后台功能与部署验证。
- 准备演示账号、样例订单、样例评价、样例游记、样例行程和模拟支付数据。

#### 6.11.4 系统合格性测试演练
- 在答辩前至少进行两轮全链路演练，分别关注“功能演示顺序”和“环境稳定性”。
- 对 AI 场景单独进行演练，确保提示词、输入样例和降级结果均可复现。

#### 6.11.5 系统合格性测试执行
- 按“首页与登录 -> 搜索预订 -> 订单管理 -> 行程与社区 -> 后台管理 -> AI 亮点 -> 部署说明”的顺序验证系统整体能力。
- 判定标准以核心链路完整、主要页面稳定、文档一致、无致命缺陷为通过前提。

#### 6.11.6 修改和再测试
- 系统级缺陷必须优先处理；若影响最终答辩主链路，则立即启动修复与复测。
- 对非关键增强功能可采用关闭入口、Mock 演示或延后展示的方式控制风险。

#### 6.11.7 系统合格性测试结果分析与记录
- 在《测试报告》中汇总系统测试覆盖范围、通过结果、遗留问题及风险说明。
- 将系统合格性测试结论作为最终交付和答辩展示的准入条件。

### 6.14 软件配置管理

#### 6.14.1 配置标识
- 建立需求基线、设计基线、代码基线、测试基线和发布基线。

#### 6.14.2 配置控制
- 任何需求、接口、数据库表结构和公共组件的变更都必须经过讨论确认后实施。

#### 6.14.3 配置状态统计
- 每周统计任务完成率、分支合并情况、缺陷数量、文档更新状态和里程碑达成情况。

- 在需求冻结、设计定稿、迭代结束、最终发布前分别开展配置审核。

#### 6.14.5 发行管理和交付
- 采用阶段性版本发布方式：架构基线版、核心功能演示版、集成测试版、最终交付版。
- 每次发布均附带版本说明、已知问题和回滚方案。

### 6.15 软件产品评估

#### 6.15.1 中间阶段的和最终的软件产品评估
- 在需求、概要设计、详细设计、各迭代结束和最终交付前分别开展产品评估。
- 评估维度包括功能完成度、缺陷情况、性能稳定性、文档一致性和演示可用性。

#### 6.15.2 软件产品评估记录
- 评估结果记录在会议纪要、任务看板、缺陷清单和版本说明中。

#### 6.15.3 软件产品评估的独立性
- 评估尽量由非原作者或 QA 牵头执行，避免仅由实现者自我判断。
- 对最终交付版本，以教师/助教的外部视角作为重要参考。

### 6.16 软件质量保证

#### 6.16.1 软件质量保证评估
- 质量保证重点关注编码规范、接口规范、数据一致性、异常处理、测试覆盖和交付完整性。
- 进入最终验收前，系统需满足“无 P0 级缺陷、核心链路可完整演示、文档与实现一致”的要求。

#### 6.16.2 软件质量保证记录、包括所记录的具体条目
- 质量记录包括 Code Review 记录、测试记录、缺陷单、版本说明、环境验证记录和里程碑评审纪要。
- 对敏感数据脱敏、AI 降级策略、服务器资源优化等质量相关事项单独留痕。

#### 6.16.3 软件质量保证的独立性
- 质量保证由 QA 角色主导，并通过交叉评审、联合评审和里程碑检查保证相对独立。
- 对公共基础能力和关键交易链路，要求至少一名非直接开发成员参与验证。

### 6.17 问题解决过程（更正活动）

#### 6.17.1 问题/变更报告
- 所有问题与变更统一通过 Issue、任务卡或缺陷单记录，至少包含编号、标题、现象、影响范围、优先级、责任人和状态。
- 需求变更需补充原因、影响分析和是否调整里程碑的判断。

#### 6.17.2 更正活动系统
- 问题处理流程为：提出 -> 受理 -> 定级 -> 修复 -> 回归验证 -> 关闭。
- 对公共模块、订单主链路和部署环境相关问题启用快速响应机制，必要时由项目经理直接协调资源处理。

### 6.18 联合评审

#### 6.18.1 联合技术评审包括一组建议的评审
- 技术评审对象包括需求划分、系统架构、数据库设计、API 设计、测试方案、部署方案和 AI 接入方案。
- 每次技术评审重点检查可实现性、接口一致性、模块边界清晰度和技术风险。

#### 6.18.2 联合管理评审包括一组建议的评审
- 管理评审对象包括进度偏差、人员投入、任务分配、风险变化、交付准备和范围控制。
- 管理评审通常在每周例会和迭代结束后进行，必要时临时召开专项协调会。

### 6.19 文档编制
- 文档编制遵循“与开发同步、按里程碑提交、提交前评审”的原则。
- 本项目需完成的软件开发计划书、需求规格说明书、概要设计说明书、详细设计说明书、测试报告、部署文档、用户手册等文档，分别由对应负责人牵头编写、团队交叉审阅。
- 文档内容必须与最终系统实现一致，图表、数据表、接口说明和测试结论需可追溯、可核验。

### 6.20 其他软件开发活动

#### 6.20.1 风险管理，包括已知的风险和相应的对策
- 重点风险包括技术学习曲线、需求范围膨胀、前后端联调阻塞、服务器资源不足、AI 接口不稳定等。
- 对策包括前期培训、范围冻结、API 优先、Mock 降级、服务器参数优化和关键链路优先保障。
- 详细风险项及应对措施见第11部分。

#### 6.20.2 软件管理指标，包括要使用的指标
- 进度指标：计划完成率、里程碑达成率、延期任务数。
- 质量指标：未关闭缺陷数、P0/P1 缺陷数、回归通过率、系统冒烟测试通过率。
- 协作指标：Pull Request 审核完成率、文档按时提交率、每日站会参与率。
- 交付指标：可演示功能覆盖率、最终文档齐套率、部署成功率。

#### 6.20.3 保密性和私密性
- 课程项目中使用的账号、手机号、证件号、订单数据等均采用模拟数据或脱敏数据。
- 对数据库中的敏感字段进行加密或脱敏展示，日志中禁止输出完整隐私信息。
- AI 输入输出中涉及用户信息时应避免不必要的原文存储。

#### 6.20.4 承包方管理
- 本项目中的“承包方”为项目开发团队，“需方”为课程教师及助教。
- 团队需按约提交文档和系统，主动反馈风险和偏差，并对交付结果负责。

#### 6.20.5 与软件独立验证与确认（IV&V）机构的接口
- 课程项目不单独设置 IV&V 机构，由 QA 角色、非原作者交叉评审以及教师/助教的阶段检查共同承担相对独立的验证职责。
- 若在课程检查中收到外部意见，项目组需形成响应记录并闭环整改。

### 10.4 关键计算机资源估算
部署服务器配置为：2核CPU、2GB内存、58GB磁盘。初步估算其能否支撑项目运行。

| 资源类型 | 预估需求 | 估算依据 |
| :--- | :--- | :--- |
| CPU | 平均负载 < 1.0 (2核) | 模拟并发用户数 < 100，Spring Boot 应用 + MySQL 查询为主要消耗。典型电商场景下，2核可支撑几十到上百并发。 |

| 磁盘 | 约 10 GB | - 操作系统: ~20GB<br>- 应用程序(JAR包、静态资源): ~1GB<br>- 数据库(初期模拟数据): ~500MB<br>- 日志文件: ~2GB (轮转策略)<br>总计：约23.5GB，远低于58GB。 |

- 为JVM设置 `-Xmx512m -Xms512m` 限制堆内存。

- 开启Nginx Gzip压缩，减少传输数据量。
- 使用 `logrotate` 对日志进行轮转和压缩。

## 12 支持条件

本项目从研发、测试到最终的评审验收，需要特定的计算机系统支持以及各干系人（需方与承包方）的相互配合。

### 12.1 计算机系统支持
1. **开发环境（Development Environment）**：
   - 硬件：团队成员各自的笔记本电脑（建议 16GB 内存及以上）。
   - 软件：IntelliJ IDEA 或 VS Code，Node.js (v18+) 运行环境，JDK (v17) 运行环境，Git 客户端，本地 MySQL 8.0 或 Docker，Redis（可选）。
   - 协作工具：GitHub（代码托管）、华为 CodeArt 或 Teambition（任务看板）、飞书/微信（日常沟通）。
2. **测试环境（Testing Environment）**：
   - 软件：Postman 或 Apifox（用于API调试与自动化接口测试），Chrome 浏览器及 Vue DevTools（前端调试）。
3. **生产/运行环境（Production Environment）**：
   - 服务器：Ubuntu 22.04 LTS (2核 2GB)。
   - 基础软件：Nginx（端口80/443）、Java JRE 17、MySQL 8.0 服务端。
   - 外部服务：高德地图Web API（获取地图模式数据）、第三方大语言模型 API 凭证。

### 12.2 需要需方承担的工作和提供的条件
本项目的“需方”在此场景下主要指**课程教师/助教**。
1. **需求确认与澄清**：在项目初期的第4-5周，需方需审阅团队提交的《软件需求规格说明书》，确认核心功能点（M1~M6）是否满足课程评分标准，并对边界模糊的需求提供指导性意见。
2. **提供验收标准与模板**：及时公布项目评分细则（Rubrics），以及各类过程文档的推荐参考模板（如需严格遵从 GB/T 8567-2006 规范，请提供明确版本）。
3. **基础设施支持（可选）**：如课程组有条件，希望能为各小组提供统一配置的校园网虚拟机或测试服务器；如无，则确认允许团队使用自行购买的云服务器作为最终部署平台。
4. **结项验收与环境**：在第15周的演示答辩环节，需方需提供投影/演示设备，并留出合理时间供团队展示系统的主体业务流及 AI 亮点功能。

### 12.3 需要承包方承担的工作和提供的条件
本项目的“承包方”为**项目开发团队**。
1. **全生命周期开发**：团队需自备开发用计算机，按时完成从需求调研、架构设计、编码实现、系统测试到最终部署的所有软件开发活动。
2. **过程文档输出**：严格按照时间节点（见第3.6节计划），交付计划书、需求规格说明书、概要/详细设计说明书、测试报告、部署文档及用户手册，并确保文档质量。
3. **质量与诚信保证**：团队需确保最终交付的“拾光旅行”平台无重大功能缺陷（主流程连通率≥99%）；**严禁直接抄袭往届作业或开源项目**。对于使用 AI 生成的代码，团队承诺经过人工严格审查并在文档中予以说明。
4. **技术支持与答疑**：在答辩验收后的一周内，承包方需保证部署在服务器上的系统正常运行，随时配合教师及助教的复查测试，解答关于代码逻辑或系统架构的疑问。
5. **知识产权声明**：项目所使用的第三方开源库均严格遵守其开源协议（如 MIT, Apache 2.0）；产生的源码和文档成果著作权归团队全体成员及学校共同所有。
