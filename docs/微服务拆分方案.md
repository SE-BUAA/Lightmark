# Lightmark 微服务拆分方案（软件工程基础实践·第二阶段）

> 对应评分项：微服务划分（7 分）、数据归属（5 分）、微服务流水线（5 分）、用例回归（4 分）、
> 自动扩缩容（3 分）、故障处理（2 分）、性能对比（4 分），合计 30 分。
> 配套材料：服务划分图、服务接口清单、数据表归属表、跨服务调用说明、改造前后代码版本、实验与性能数据。

---

## 1. 背景与拆分原则

### 1.1 现状（单体）

- Spring Boot 3.5 单体，核心域：**用户/认证、产品（机票/酒店/火车票/度假）、订单/交易、内容（社区/智能行程/AI）**。
- 数据库：单 MySQL `lightmark` 库，约 19 张业务表。
- 单体通用 CRUD（`CrudController/{table}`、`ModuleController`、`GenericCrudService`）可动态读写任意表——**拆分后必须消除**，改为各服务暴露自己的领域接口。

### 1.2 拆分原则（对应题目要求）

1. 按**业务域**划分，不按用例数量机械拆分；
2. 至少 3 个**业务**微服务（网关/注册中心/配置中心/前端/数据库不计入）；
3. 每张表**唯一归属**一个服务，其他服务不得直连表，跨服务一律走接口/事件，并说明失败处理；
4. 每个服务可**独立构建、测试、部署**、独立扩缩容；
5. 同一 MySQL 服务器、不同 **Schema**，不跨服务联表查询。

## 2. 方案总览：4 个业务微服务

| 服务 | 端口 | 业务职责 | 独立可部署 |
| --- | --- | --- | --- |
| **user-service** | 8081 | 认证、验证码、用户资料、角色权限、常用出行人、积分会员、登录日志、管理员操作日志 | ✅ |
| **product-service** | 8082 | 机票/酒店/火车票/度假产品目录、房型、搜索/价格日历、浏览记录、库存 | ✅ |
| **order-service** | 8083 | 各类产品下单、支付、退款、改签、取消险、发票、订单评价、订单聚合查询 | ✅ |
| **content-service** | 8084 | 智能行程、AI 助手、社区游记/评论/点赞/问答 | ✅ |

> 可选：**Spring Cloud Gateway 网关**（不计业务服务）统一 `/api/*` 路由与 JWT 透传；
> 本方案默认先用 **Traefik Ingress 按前缀路由**，网关作为加分项。

### 项目结构

```
lightmark/
├── backend/                  # 单体（保留！monolith-start 标签对照用）
├── msa/                      # 微服务目录（新代码）
│   ├── pom.xml               # 父 POM（公共依赖、版本管理）
│   ├── lightmark-common/     # 公共模块：ApiResponse、JwtTokenService、异常、工具
│   ├── user-service/         # 独立 pom + src + test
│   ├── product-service/
│   ├── order-service/
│   └── content-service/
├── .github/workflows/        # 一个流水线，matrix 分别构建 4 个服务
└── deploy/k8s/msa/           # 每服务独立 Deployment/Service/HPA
```

- **单独编译**：`mvn -pl user-service -am package`（只编 user-service + 它依赖的 common）
- **单独测试**：`mvn -pl user-service -am test`
- **单独部署**：每个服务独立镜像 `user-1.0.x`、独立 Deployment/Service/HPA
- **模块间规则**：只能依赖 `lightmark-common`，**不能依赖其他 service 模块**（强制数据/调用隔离）

## 6. 跨服务调用与失败处理

### 6.1 主要调用链

**链 1：下单（order → product → user）**
```text
用户下单(order-service)
  ├─ ① GET /internal/product/{productId}       （校验在售、取价格）
  ├─ ② POST /internal/product/{id}/stock 扣库存
  ├─ ③ 写 orders / payment_record（本地事务）
  └─ ④ POST /internal/user/{id}/points 加积分   （异步/补偿）
取消/退款时：回补库存（②）、撤销积分（④）
```

**链 2：内容展示（content → user）**
```text
社区列表(content-service) → GET /internal/user/{id} 补昵称/头像（可本地缓存昵称字段，降级用）
```

### 6.2 失败处理策略（Resilience4j + 补偿）

| 场景 | 策略 | 用户看到 |
| --- | --- | --- |
| product 服务慢/挂 | 超时 3s + 重试 1 次 + 熔断（半开恢复）；下单前校验失败 | "服务繁忙，请稍后再试"；已扣库存 30 分钟未支付自动回补 |
| user 积分服务挂 | 下单**本地事务先成功**，积分走异步重试/补偿表（outbox），后台任务补发 | "下单成功，积分稍后到账" |
| content 取用户昵称失败 | 降级返回本地冗余字段/默认昵称 | 列表正常展示 |
| 任意依赖不可用 | 熔断器快速失败，不拖垮本服务线程池；各服务独立 Deployment，不级联崩溃 | 友好错误提示 |

### 6.3 数据一致性（不用分布式事务）

- 下单主链路用**本地事务**（orders + payment_record + 预扣库存标记）；
- 库存扣减以 product 服务为准（接口原子操作 + 超时释放）；
- 积分/评价等次要操作用**异步补偿**（本地 outbox 表 + 定时重试），达到最终一致；
- 答辩时明确说明：为什么不用 2PC/Seata，用"最终一致 + 补偿"。

## 7. 数据库拆分与迁移

1. 同一 MySQL 服务器创建 4 个 schema：
   ```sql
   CREATE DATABASE lightmark_user CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   CREATE DATABASE lightmark_product ...;
   CREATE DATABASE lightmark_order ...;
   CREATE DATABASE lightmark_content ...;
   ```
2. 编写 `scripts/db/split-mysql.sh`：按 §4 归属表，把现有 `lightmark` 各表 `mysqldump` 到对应 schema（保留数据），并删除原库表（或保留原库作为单体版对照数据源）。
3. 每个服务独立 Flyway（`db/migration/user/*.sql` 等），迁移文件按服务目录归位；`flyway_schema_history` 各自独立。
4. 现有 Flyway 迁移文件（V20260527…V20260612）按涉及的表拆分归档到对应服务；基准库以 `monolith-start` 导出的数据为基线。
5. 应用配置：每服务 datasource 指向自己的 schema，账号最小权限（user 只连 user schema）。

## 8. 代码拆分路线（步骤化）

| 步骤 | 内容 | 产出 |
| --- | --- | --- |
| S1 | 抽公共模块 `lightmark-common`（ApiResponse、JwtTokenService、异常、分页、工具类）打成 jar | 共享依赖 |
| S2 | 建 4 个 Spring Boot 工程（Maven 多模块或独立仓库），统一 JDK17/Spring Boot 3.5 | 工程骨架 |
| S3 | 迁移 controller/service/dao：Auth/User/Points/Membership → user；PublicApiController(flights 搜索)、FlightSearchService(搜索部分)、Hotel 搜索、Train 搜索、Vacation 搜索、ModuleController(只读模块) → product；OrderController/OrderServiceImpl、flights order、Hotel 订单、Train 订单、Vacation 订单 → order；Community/Conversation/Itinerary/AI → content | 代码迁移 |

| S5 | 跨服务调用落地：WebClient + Resilience4j；JWT 共享密钥校验（各服务校验，或网关校验透传） | 服务间通信 |

| S8 | 全量回归：单元 + 集成 + API 级端到端（按用例清单） | 回归报告 |

## 9. CI/CD 与 Kubernetes 部署（每服务独立）

- **流水线**：一个 workflow 用 matrix 构建 4 个服务（或每服务独立 workflow）；每服务：`mvn test`（单元+集成）→ 原生打包 jar → 多架构镜像（amd64+arm64）→ 推 GHCR（版本号 `<svc>-1.0.<run>` + `sha-<commit>`）→ 部署对应 Deployment；
- **任何一步失败即停**，成功/失败记录保留（复用现有机制）；
- **K8s**：每服务 `Deployment + Service + HorizontalPodAutoscaler + 资源 requests/limits`，`deploy/k8s/msa/` 目录新增 4 组文件；Ingress 增加前缀路由（/api/auth、/api/user → user-service 等）；
- **健康检查**：每服务保留 `/api/health`，探针指向各自服务；部署脚本按服务依次 `apply + rollout + healthcheck`（复用 deploy-k8s.sh 模式，扩展为多服务）；
- **版本号**：`kubectl get deploy <svc> -o jsonpath='{.spec.template.spec.containers[0].image}'` 可查；服务日志 `kubectl logs deploy/<svc>`。

## 10. 云原生实验

### 10.1 自动扩缩容（3 分）

- 每服务 Deployment 配置 `resources: requests:{cpu:250m,memory:512Mi} limits:{cpu:1,memory:1Gi}`；
- HPA：`kubectl autoscale deploy order-service --min=1 --max=5 --cpu-percent=60`；
- 压测：`ab -n 20000 -c 200 http://<host>/api/orders?...` 或 k6 脚本；
- 记录：Pod 数量变化、吞吐、平均/P95 响应时间、错误率（原始数据归档 `04_tests/load/`）。

### 10.2 故障处理（2 分）

- 演示：`kubectl scale deploy product-service --replicas=0`；
- 预期：下单接口超时 → 熔断打开 → 返回设计好的提示（"服务繁忙，请稍后再试"）；user/content 服务不受影响；
- 恢复：`kubectl scale deploy product-service --replicas=1` → 熔断半开自动恢复；
- 记录：故障期间各服务错误率/响应时间、熔断日志。

## 11. 性能对比（4 分）

| 项 | 要求 | 做法 |
| --- | --- | --- |
| 对照版本 | monolith-start 标签 vs 微服务版 | 先打标签并冻结 |
| 环境 | 同一台机器 | 均部署到同一 k3s 服务器（或同一台机器 docker compose/k3s） |
| 数据 | 同一批数据 | 微服务版从 monolith 导出导入，保证一致 |
| 脚本 | 同一压测脚本 | 同一 ab/k6 脚本，参数一致 |
| 次数 | 各 ≥3 次 | 取 3 次结果全部归档 |
| 指标 | 并发数、吞吐、平均/P95、错误率、CPU/内存 | `ab` 输出 + `kubectl top` / `docker stats` |
| 接口 | 选 2–3 个主要接口 | 如 `/api/flights/search`、`/api/orders/{no}/pay`、`/api/hotel/list` |
| 结论 | 慢也允许，必须解释 | 分析网关/序列化/网络开销，给真实数据与原因 |
