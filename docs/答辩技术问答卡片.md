## 一、架构与微服务划分

### Q1 为什么拆成 4 个服务?划分依据是什么?
**按业务域划分 + 每张表唯一归属;跨服务只走接口,不跨库联表;先消除单体的"任意表 CRUD"设计债。**
- 4 服务职责:user=认证信任根(登录/会话/资料);product=只读产品目录(机票/酒店/火车/度假,含 MCP 查票);order=交易状态机(订单/支付/退改);content=内容与 AI(社区/DeepSeek,故障只降级不影响交易);
- 划分不是按用例数机械切,而是按"领域模型边界 + 数据归属"切;
- 证据:20 张单体表迁移 + 2 张 MSA 新增表(`hotel_order_detail`/`invoice_application`),全量归属表见微服务划分文档 §5。

### Q2 跨服务拿数据怎么做?
**只允许 internal HTTP 接口,禁止跨 schema 直查/联表。**
- 例:下单校验乘车人 → order 调 user `/internal/user/{id}/travelers`;校验产品取价/扣库存 → order 调 product `/internal/product/{id}`、`/{id}/stock`;
- 内部接口带"服务身份"JWT(角色 SERVICE),不是用户令牌;
- 外部大表(如 product 948 行/orders 99 行)的一致性用拆分后 row count 抽查验证。

### Q3 为什么 4 个 schema 仍在同一台 MySQL,不算"分库"吗?
**同一服务器多 schema 是教学与资源约束下的部署形态;隔离靠"最小权限账号 + 接口边界"保证,服务间无共享账号直连。**
- 每个服务 Secret 只配本 schema 权限(部署脚本自动 GRANT);
- 若要独立实例,接口与代码不变,只改连接串——这是"数据归属唯一"的收益;
- 拆分脚本 `scripts/db/split-mysql.sh` 幂等可重跑,保留单体库作对照。

### Q4 为什么强调消除通用 CRUD?(PPT 讲稿 Q6)
**"任意表读写"会让表归属失去意义、接口没有边界,是单体迁微服务前必须先拆的雷。**
- 单体存在 `CrudController/{table}`、`GenericCrudService` 可写任意表;
- MSA 中每张表只有唯一属主服务能读写,其他服务只能经其 internal 接口——归属与边界从代码层面强制。

## 二、数据一致性与事务

### Q5 拆库之后跨服务数据怎么保证一致?(PPT 讲稿 Q2)
**主链路本地事务 + 内部接口 + 超时重试熔断;写类副作用走 outbox 异步最终一致,不做分布式事务。**
- 积分增减:下单本地事务先成功 → 写 `order_outbox` 表 → `@Scheduled` 5s 轮询调 user 积分接口,失败 30s 后重试 → 用户看到"下单成功,积分稍后到账";
- 库存:下单扣减(调 product internal),超时未支付自动回补兜底;
- 不做 2PC/分布式事务:复杂度高、锁放大,业务上可接受最终一致(有迁移 `V20260831__order_outbox.sql` 为证)。

### Q6 内部接口调用失败会不会把下单流程卡死?
**不会:3s 超时 + 重试 2 次(300ms)+ 熔断(10 窗口 5 失败开 10s),兜底统一 503"服务繁忙,请稍后再试"。**
- 见"六、熔断与可靠性"卡片,演示即验证。

## 三、会话与安全

### Q7 登录会话为什么需要"粘滞"?粘滞怎么做?
**验证码/登录依赖进程内存 HttpSession;多副本下会话会漂移,所以把有状态会话收敛在 user-service,并用 Traefik sticky cookie 固定副本。**
- cookie 名 `lm_user_session`,IngressRoute 只对 `/api/auth` 生效(`deploy/k8s/msa/user-auth-sticky.yaml`);
- 其余服务无会话状态,可自由水平扩缩容;
- 追问"为什么不用 Redis 会话?"→ 收敛 + 粘滞是当前规模下的最简解;Redis 化在展望清单里。

### Q8 JWT 怎么跨服务认证?
**user-service 用共享密钥签发(HS512,密钥 ≥32 字节),order/product/content 只做校验;服务间调用使用服务身份令牌。**
- 用户令牌身份含 USER/ADMIN,admin 接口校验身份;
- 修复案例:content 调 user internal 取昵称曾**没带令牌**被 401,导致昵称恒为"旅行用户"(见 Q10)——补上服务令牌后基线昵称恢复真实值。

## 四、火车票与 MCP(演示主线用例)

### Q9 火车票数据为什么不在数据库里?(PPT 讲稿 Q3)
**12306 是实时外部数据源,不由我们持久化;本地只维护站点字典 station.csv(3100+ 站)做联想,车次/余票经 mcp-12306-server 实时查询。**

### Q10 MCP 会话怎么建立的?失败怎么办?(PPT 讲稿 Q1)
**三步握手:initialize → 保存响应头 Mcp-Session-Id → 回发 notifications/initialized;此后每次 tools/call(如 query-tickets/query-transfer)必须带会话头,无会话会被服务端拒绝(-32000 Invalid session ID)。**
- 会话收敛在 product-service 内管理(synchronized 保证单会话复用);
- 失败处理:调用异常时重置会话并**自动重建、重试一次**;仍失败返回空结果(`success:false`),不抛 500,不影响机票/酒店等其他域(故障隔离);
- 工具名是连字符命名(query-tickets 而非 queryTickets),这是 MCP 协议约定,对接时踩过坑(可作复盘谈资)。

### Q11 火车票购买用例跨了几个服务?(3 分钟讲解 P2 的口径)
**user(登录/会话)→ product(查票,经 MCP)→ order(下单:校验产品价与库存、校验乘车人归属后本地事务落库);订单域 `orders`/`payment_record` 属 order,乘车人 `traveler` 属 user——跨服务只走 internal 接口。**

### Q11+ 火车票查询为什么选开源 MCP 容器,而不是商用或自建 API?
**12306 没有对外提供官方/商用授权的开放查询 API;商用聚合平台需要企业资质、签约与费用,个人/教学项目拿不到;自建爬虫要对抗官方会话、验证码与风控,成本高、不稳定且有合规风险。该开源 MCP Server 把 12306 实时查询(余票/中转/车站)封装成标准 MCP 工具、容器化一键部署,是课程项目工程成本与风险都最低的接法。**
- 为什么不用商用 API(携程/同程等开放平台):需企业资质审核、签约付费;部分聚合数据非实时、含平台加价;
- 为什么不自建爬虫:12306 Web 端有登录会话、验证码与风控,逆向与持续维护成本高,不适合作为演示依赖;
- 为什么是 MCP 形态:协议标准化(JSON-RPC 2.0 + initialize 会话握手),与我们"微服务经 HTTP 对接外部依赖"的方式一致;查询能力被抽象为语义化工具(query-tickets / query-transfer),会话由 MCP Server 集中管理,我们只需维护 Mcp-Session-Id;
- 部署与演练价值:它是**独立外部容器**(宿主机 9000→8000,`scripts/deploy-mcp-12306.sh` 一键拉起),与微服务同构——演示中它就是"外部依赖故障"的天然注入点:火车查票失败不影响机票/酒店,与故障隔离演示呼应;
- 如实口径:社区开源封装([mcp-server-12306 项目家族](https://github.com/drfccv/mcp-server-12306),本项目使用其容器化镜像 ghcr.io/supikatsujikura/mcp-12306-server),用途是**教学演示与低频查询、不涉及购票交易**;生产/商用应走官方合作或合规授权渠道。

## 五、性能实验与 HPA

### Q12 单体 6.9k rps vs 微服务单副本 70 rps,差 ~100 倍怎么解释?(PPT 讲稿 Q4)
**差距来自部署形态而非架构:微服务单副本 CPU limit 500m + Hikari 默认 10 连接 < 压测并发 30,造成排队型长尾;同一 MySQL 在单体侧可达数千 rps,证明瓶颈不在数据库。**
- 证据:p95 是 avg 的 60 倍左右(排队特征);4 副本聚合吞吐随副本数上升,且 3 万请求 0 失败;
- 微服务的价值是**弹性与隔离**,不是单点性能;如实表述:"单副本受资源限额影响约为单体的 1/100,横向扩展由 HPA 实验验证"。

### Q13 为什么不能说"微服务性能提升"?
**同机同数据同脚本的实验(admin 三接口)两版性能几乎一致、0 错误,唯一稳定差异是微服务内存高约 30–40MB(独立 JVM);如实口径才经得起追问。**

### Q14 HPA 的工作原理?(结合演示)
**控制回路:容器 CPU → metrics-server → HPA 控制器(约 15s 评估)→ 调整 Deployment 副本数。**
- 利用率 = 实际用量 ÷ **requests**(100m=0.1 核 CPU,不是内存;product request cpu 100m / limit 500m);
- 期望副本 = ceil(当前副本 × 当前利用率 ÷ 目标 60%),夹在 min=1/max=4;
- 细节:新 Pod 就绪前(冷启动 50–90s)不计指标,所以 1→2→4 是阶梯式;缩容有容忍区(±10%)与稳定窗口,避免抖动,所以 4→2→1 分步回落;
- metrics-server 无数据时 HPA 显示 `<unknown>` 且不动作(演示预检时见过,属正常冷启动现象);
- 演示数据:CPU 3m → ab 加压 → 185%/482% → 1→2→4;3 万请求 0 失败;停压 CPU 2% → 4→2→1。

### Q15 为什么故障演示要先"暂停 HPA"?
**HPA min=1:不停 HPA 直接缩到 0 会被控制器拉回,演示失效。恢复服务后脚本自动重建 HPA(min1/max4/CPU60%)——"演练与扩缩容策略需协同"是个加分细节。**

### Q16 压测怎么保证公平?
**同机、同数据源、同脚本、同并发;每接口每版本 3 轮取中位数;错误率与原始 CSV 全部留档(`artifacts/load/`)。**

## 六、熔断与可靠性(演示核心)

### Q17 这次"熔断"具体是什么配置?怎么触发的?
**order-service 对 product 的调用上叠加:WebClient 3s 超时 → @Retry(2 次,间隔 300ms)→ @CircuitBreaker(滑动窗口 10、最少 5 次调用、失败率 50%、打开 10s);fallback 统一抛 503"服务繁忙,请稍后再试"。**
- 状态机:CLOSED(计数)→ 窗口内 ≥5 次失败且失败率 ≥50% → OPEN(10s 内不再发网络请求,直接快速失败)→ 10s 后 HALF_OPEN(放行 1 个试探)→ 成功回 CLOSED / 失败回 OPEN;
- 演示数字:依赖缩容到 0 后,8 次预览全部 503 + 统一文案,单次 326–458ms(= 300ms 重试间隔 + 两次快速连接失败);熔断窗口 3/3 快速失败;恢复后第一个请求是半开试探 → 200(384ms)→ 熔断闭合自愈。

### Q18 熔断打开后为什么还有 ~350ms,不是 0ms?
**重试注解在调用链外层:即使熔断不再发起网络请求,每轮仍保留 300ms 重试等待。真正对比是:若依赖"挂起"而非"拒连",未熔断时每次要等 3s 超时×2 ≈ 6.3s;熔断后无论依赖何种故障都 ~350ms 快速失败——保护效果体现在"不再等待网络超时"。**

### Q19 为什么用 /api/flights/order/preview 演示?
**免鉴权、无副作用(只计价不写库不扣库存),可安全连打;且它内部必经 product 校验,正好命中熔断注解所在链路。**

### Q20 503 之前为什么返回 400?(复盘,可主动讲)
**order-service 的异常处理 `statusFor` 只映射了 401/403/404,503 落到 default 400;已补齐 400/409/500/503 映射(与 common 版对齐)。这是"配置与设计意图不一致"被接口实测抓出的案例。**

### Q21 备用结果/降级都有哪些实现?(演示 A + 设计)
- 社区昵称:user 故障 → 默认昵称"旅行用户"(1s 连接/2s 读超时兜底);
- 熔断文案:503"服务繁忙,请稍后再试";
- 积分:outbox 异步"稍后到账";
- AI:密钥缺失/调用失败 → 降级文案或模板行程;
- 隔离保证:各服务独立 Deployment + 独立 schema + 熔断快速失败,不级联崩溃(演示 C:content 下线,机票/酒店/订单/登录全正常)。

## 七、测试与 CI/CD

### Q22 测试规模与质量门禁?
**单体 28 个测试文件;MSA 20 个(公共 2/用户 9/产品 6/订单 2/内容 1),单元+集成;依赖外部 DB/密钥的用例按环境变量门控,未配置自动跳过,保证流水线确定性;`mvn test` 全绿是发布门禁。**

### Q23 测试报告交哪个阶段?
**拆微服务后仍要测试,报告交第二阶段(老师明确答复);两阶段测试文档齐全(`docs/test/`、`docs/testing/`)。**

### Q24 CI/CD 怎么组织的?
**双流水线:develop(单体)与 msa-develop(微服务),镜像版本化 `1.0.<run>` + 部署时记录 deploy-history.log;失败即停,部署失败自动回滚上一版本;服务器环境以 ~/lightmark/.env.k8s 优先于 GitHub Secret(SERVER_ENV_BASE64)。**
- 为什么不用 latest:版本化 tag 才能回滚与追溯(镜像 tag 曾因仓库名大小写踩坑,GHCR 要求小写,已统一 lower-case)。

### Q25 微服务与前端有哪些契约坑?

## 九、演示细节答疑

### Q26 场景 A 的游记是"假数据"吗?
**是直接写入内容库的一条 status=1 种子记录(作者为库中真实用户),与运营录入等价;演示链路本身是真实 API:GET /api/posts → content 调 user 补昵称 → 停 user → 降级"旅行用户" → 恢复还原。**

### Q27 为什么恢复要等几十秒?视频里能剪吗?
**缩容到 0 后冷启动需 50–90s(JVM + Spring Boot),脚本自动等 rollout;录屏可加速/剪掉等待段,断言输出保留即可。**

### Q28 故障演示脚本安全吗?
**全自动 + 兜底:预检自动等 Ready;停服前暂停 HPA、恢复后重建;Ctrl+C 也会恢复现场;可反复跑,31 项断言全绿。**

## 十、总结口径(收尾用)

**两阶段交付闭环:单体还原为可部署工程(容器化/测试/CI)→ 按业务域拆 4 微服务(表唯一归属、接口边界、internal 调用)→ 双流水线自动部署 K8s → HPA/熔断/故障演练/性能对比全部实测留档;过程中暴露并修复的真实问题(异常码映射、内部令牌、契约字段、会话漂移)正是工程实践的价值。**
