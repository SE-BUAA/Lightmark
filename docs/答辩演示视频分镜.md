## 2. 故障注入段口播(约 80–90s,与字幕并行)

> 我们演示故障处理。场景一,停止用户服务:登录立即 503,但机票搜索、订单预览不受影响——这是故障隔离;社区列表依然 200,只是作者昵称按设计降级为"旅行用户",这是备用结果;恢复服务后昵称自动还原,服务自愈。
>
> 场景二,停止产品服务,订单服务下单前的价格与库存校验失去依赖:连续 8 次请求全部返回 503"服务繁忙,请稍后再试"——每次失败都经过 300 毫秒间隔的重试,再把设计好的提示交给用户,不暴露内部错误;连续失败触发熔断,熔断打开期间 3/3 请求被瞬时拦截、快速失败,保护订单服务自身不被拖垮;恢复产品服务后,熔断半开试探成功、自动闭合,服务自愈。
>
> 场景三,停止内容服务:社区 503,但机票、酒店、订单、登录全部正常——一个服务下线不拖垮任何其他业务域。恢复后立即回到 200。全程 31 项断言零失败。

## 3. HPA 段字幕(按 12:27 运行输出)

| # | 画面锚点 | 字幕 |
| --- | --- | --- |
| H1 | `HPA product-service: min=1 max=4` | HPA:副本 1–4,CPU 60% 触发 |
| H2 | `阶段1 基线 … cpu=3m` | 基线:1 副本,CPU 0.3% |
| H3 | `ab -n 30000 -c 100` | 加压:ab 并发 100,3 万次搜索请求 |
| H4 | `cpu=185m→482m` / `replicas=1/2→2/2` | CPU 超阈值 → 自动扩容 1→2 |
| H5 | `cpu: 140%/60% REPLICAS 4` | 压力持续 → 继续扩容至 4 副本 |
| H6 | `Complete requests: 30000 / Failed: 0` `89.56 rps` `95% 2829ms` | 3 万请求 0 失败 · 吞吐 89.6/s · P95 2.8s |
| H7 | `cpu=2m` → `replicas=4/4→2/2→1/1` | 停压:CPU 回落,自动缩容 4→2→1 |

HPA 段口播:压力升,副本增;压力降,副本减——全程 3 万请求零失败,扩缩容无需人工干预。(数值口径:单机小规格 + 单副本 500m CPU 限额,展示的是压力下的可用性与弹性,不作"性能提升"表述。)
