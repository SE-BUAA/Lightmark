# Lightmark 拾光旅行 —— 软件工程基础实践技术总结报告

> 项目:在线旅游平台(机票/酒店/火车票/度假 + 智能行程/AI + 社区 + 管理后台)
> 阶段:第一阶段(单体还原/容器化/CI/CD)+ 第二阶段(微服务拆分/K8s 部署/云原生实验/性能对比)
> 本报告对应交付项"技术总结报告",与 `docs/微服务划分.md`、`docs/部署检查单.md`、测试报告与压测原始数据配套。

---

## 1. 项目概述与总体完成情况

Lightmark 为课程大作业平台,覆盖四类产品的查询与交易闭环。实践按任务书分两个阶段推进:

| 阶段 | 目标 | 完成情况 |
| --- | --- | --- |
| 第一阶段 | 原系统可启动、补文档测试、容器化、跑通 CI/CD | 完成:单体冻结标签 `monolith-start`;前后端与数据库容器化;develop 分支流水线五段门禁全绿 |
| 第二阶段 | 拆分 ≥3 业务微服务、自动部署 K8s、扩缩容/故障/性能实验 | 完成:4 业务服务 + 4 schema + 独立 Flyway;msa-develop 独立流水线;HPA/性能对比数据归档 |

**总体数据**:4 个业务微服务(user/product/order/content)+ 1 个公共模块;同一 MySQL 服务器 4 个 schema 共 22 张表(20 张单体迁移 + 2 张 MSA 新增);前端共用同一 Vue3 SPA;两条 GitHub Actions 流水线;GHCR 版本化镜像(`<svc>-service-1.0.<run>`);k3s(Traefik)承载全部部署。

## 2. 架构演进:从单体到微服务

### 2.1 单体基线(对照对象)

- 单 Spring Boot 进程 + 单 MySQL 库 `lightmark`(20 张业务表);
- 存在**通用 CRUD 直连任意表**的设计(`CrudController/{table}`、`ModuleController`、`GenericCrudService`),表与业务无归属约束;
- 单一进程无法独立构建/部署/扩缩容,故障无隔离。

### 2.2 微服务划分(原则与结果)

按**业务域**划分而非按用例数量:认证信任根(user)、只读产品域(product)、交易状态机(order)、内容与 AI(content)。划分依据与逐表归属、接口清单、跨服务调用见 `docs/微服务划分.md`(实现现状版,以代码为准)。

关键设计决策:

1. **每表唯一归属 + 同服务器分 Schema**:跨服务一律 internal HTTP API,不做跨库联表;
2. **拆分脚本幂等**:`scripts/db/split-mysql.sh` 将 20 张单体表按归属 mysqldump 至 4 个 schema,保留单体库作对照数据源;拆分带入的跨 schema 外键由迁移 `V20260902` 动态清理;
3. **独立 Flyway**:各服务独立迁移目录与历史表,`hotel_order_detail`/`invoice_application` 作为 MSA 新增表由 order-service 自建;
4. **会话收敛**:验证码/登录依赖进程内存 HttpSession,收敛在 user-service 并配套 Traefik 粘滞路由(cookie `lm_user_session`),使多副本下登录不漂移;其余服务无状态可自由扩缩容;
5. **消除通用 CRUD**:MSA 无任何"任意表读写"入口,每服务仅暴露领域接口。

### 2.3 部署拓扑

浏览器 → Traefik Ingress(按 Host+路径前缀)→ 4 服务/前端 SPA;k8s 内 MySQL(pod,数据在 PVC)承载 4 schema;
火车票数据源 mcp-12306-server 与 AI(DeepSeek)、对象存储(Oracle PAR)为外部依赖。

## 3. 关键工程实践

### 3.1 容器化与数据库初始化

- 前端:Vue CLI 产物 → nginx 镜像(SPA history 回退);后端/微服务:多阶段 Maven 构建 → temurin JRE(非 root、探针、资源限额);
- 数据库:官方 `mysql:8.0.43`,数据卷为空时自动执行 `database/lightmark.sql`(Compose 挂载 / k8s ConfigMap 两种方式),增量由 Flyway 接管;
- 本地微服务:单一 compose(6 容器)一键拉起,nginx 前缀路由复用 Ingress 同款规则,支持 local/remote 两种前端 API 模式。

### 3.2 CI/CD(两条流水线)

| 流水线 | 分支 | 阶段 | 门禁 |
| --- | --- | --- | --- |
| deploy.yml(单体) | develop | 后端测试 → 前端构建 → 镜像(1.0.<run>+sha)→ SSH 部署 k3s → 公网健康检查 | 任一步失败即停;失败自动回滚上一版本 |
| msa-deploy.yml(微服务) | msa-develop | MSA 全模块测试 → 4 服务镜像矩阵 + 前端镜像 → 一键部署(含 MCP/分库/Secret/粘滞路由/滚动)→ 入口健康检查 | 同上;成功/失败写入服务器 deploy-history.log |

镜像仅按版本号与 sha 部署,不使用 latest。

### 3.3 可观测与运维

每服务 Deployment/Service/HPA(min1/max4,CPU 60%)、startup/readiness/liveness 探针、资源 requests/limits(100m/256Mi–500m/768Mi)、滚动更新 `maxSurge=0`(小节点不超容量);日志与镜像版本号命令见部署检查单 F 段。

## 4. 测试与质量保证

- **测试体系**:单体 28 个测试文件;MSA 20 个测试文件(公共模块 2/用户 9/产品 6/订单 2/内容 1),覆盖单元与集成;依赖外部 DB 的集成用例以环境变量门控,未配置自动跳过,保证流水线确定性;

- **回归验证**:跨形态一致性以实测方式核对(同一数据源 row count 抽查、接口返回对比),关键接口的"单体↔微服务"返回一致性作为验收依据之一。

## 5. 云原生实验与性能对比

### 5.1 实验一:本地同机对比(仓库归档,可复核)

实验脚本 `artifacts/load/perf_compare_local.py`,自动生成报告 `artifacts/load/perf-compare-local-20260903-160443/report.md` 与逐轮原始数据(summary.csv / *-raw.csv / *-metrics.csv)。

条件:同一台机器;单体 `backend`(端口 18082)vs `msa/user-service`(端口 18081);两边同一套对齐的管理员账号,分别连本机 H2 内存库(同构 schema + 对齐数据);并发 20、每轮 600 请求、每接口每版本 3 轮;1s 间隔采样 Java 进程 CPU/RSS。选定接口:管理端登录(POST /api/auth/admin/login,BCrypt 校验)、用户列表(GET /api/admin/users)、操作日志(GET /api/admin/logs)。

三接口均值汇总(错误率全部 0%):

| 接口 | 版本 | 吞吐(rps) | 平均(ms) | P95(ms) | CPU均值 | 内存均值(MB) |
| --- | --- | --- | --- | --- | --- | --- |
| admin_login | 单体 | 99.82 | 180.18 | 198.35 | 1545.6% | 172.6 |
| admin_login | 微服务 | 99.83 | 179.10 | 197.77 | 1542.6% | 200.3 |
| admin_users | 单体 | 297.27 | 46.60 | 66.98 | 41.7% | 189.4 |
| admin_users | 微服务 | 297.70 | 46.49 | 65.54 | 35.2% | 228.5 |
| admin_logs | 单体 | 297.63 | 45.25 | 62.90 | 25.0% | 191.1 |
| admin_logs | 微服务 | 297.93 | 45.25 | 63.74 | 30.3% | 227.3 |

**结论(忠实于数据)**:同机、同数据、同脚本、同并发下,微服务版与单体版整体性能**接近,未观察到显著性能提升**;两版均 0 错误。登录接口瓶颈在 BCrypt,与架构无关,两边几乎一致;轻量读接口受本地 H2 + 单 JVM 场景限制,网络拆分开销未体现。**可观测的差异是微服务内存常驻更高约 30–40 MB**(独立 JVM 需加载完整 Spring Boot 容器/连接池)。

### 5.2 实验二:服务器 K8s 环境对比(归档于服务器 artifacts/load/perf-compare-*/)

压测脚本 `scripts/loadtest/perf-compare.sh`(服务器运行),针对产品域接口,原始 CSV 与 summary 归档在服务器。**环境差异须说明**:微服务版为 k3s 单副本,受资源限额(CPU limit 500m)与 Hikari 默认连接数限制;单体为无该限额的常驻进程。抽测结果:

- 查询类接口(flights/hotel 等):单体数千 rps;微服务单副本约 40–80 rps(CPU 饱和),P95 长尾来自连接池排队;
- HPA 加压至 4 副本时合计吞吐显著上升但仍 CPU 饱和,证明该场景瓶颈在**单实例 CPU/连接池**,而非数据库(同一 MySQL 在单体侧可达数千 rps)。

**结论**:微服务以弹性换单点性能——拆分本身不提升单机吞吐,价值在**横向扩展、故障隔离与独立发布**(由 5.3 HPA 实验验证);单点差距可通过调大连接池、加副本、限流与 SQL 下推改善(列入展望)。

### 5.3 实验三:HPA 自动扩缩容(服务器归档:artifacts/load/hpa-*/)

对 product-service 加压(`ab -n 30000 -c 100` 压 /api/flights/search):

- 空闲 CPU 约 5%;加压后瞬时 CPU 达 453%(对 60% 阈值的数倍)→ 副本 1 → 2 → 4(max),全程 30 000 请求 **0 失败**;
- 停压后 CPU 回落,HPA 经稳定期自动缩回 min=1;
- 2s 采样时间线(timeline.log)完整记录"压力升→Pod 增、压力降→Pod 减"的完整过程。

## 6. 主要问题与解决方案(工程复盘)

| # | 现象 | 根因 | 解决方案 |
| --- | --- | --- | --- |
| 1 | user-service CrashLoop | `application.yaml` 重复顶级键 lightmark → YAML 解析失败 | 合并配置块 |
| 2 | 启动报 No default constructor | 多构造器 Bean 未标 @Autowired(头像上传功能引入) | 主构造器加 @Autowired,并全仓扫描同类风险 |
| 3 | 登录 500 internal error | 浏览器 User-Agent 超长写入 varchar(100) 的登录日志 | 仓储层按列宽截断(ip 45/device 100) |
| 4 | 登录 captcha expired | 会话在多副本间漂移 / 重建后旧会话 | Traefik IngressRoute + sticky cookie;文档化"部署后 F5" |
| 5 | 机票页恒 0 条 | 前端发机场码(PEK),数据存城市码(BJS),MSA 朴素全等 | 移植单体的机场码↔城市码归一化 + 多字段/包含匹配 |
| 6 | 酒店"暂无匹配酒店" | 前端读 `records`,MSA 分页只出 `list` | PageResponse 双字段别名(records+list)全局兼容 |
| 7 | 火车站点下拉为空 | options 返回键名与前端契约不符 | 对齐 `startStations/endStations/dates`,接入 3100+ 站 station.csv |
| 8 | order-service 迁移失败 | Flyway 迁移含 DELIMITER/存储过程,校验和不一致 | 重写为 PREPARE/EXECUTE 动态 SQL(幂等),清理历史行 |
| 9 | 头像上传失败 | Oracle PAR 过期(HTTP 401) | 重新生成 PAR 并同步 .env/server.env/代码兜底三处 |
| 10 | 微服务部署滚动超时 | 小节点容量不足(新旧副本并存) | 降资源请求 + maxSurge=0 |
| 11 | msa.lightmark.ortus.top 打不开 | DNS 未配 + Cloudflare 两层子域无边缘证书 | 灰云直连 + 源站证书策略;文档化两种方案 |
| 12 | 流水线镜像构建失败 | 仓库名大小写(GHCR 要求小写) | 镜像 tag 统一 lowercase 输出 |

复盘结论:本阶段暴露的问题集中在"跨团队代码契约"(前端参数/返回字段、配置与 Bean 构造)、
"跨环境一致性"(会话、资源、DNS/证书)与"外部依赖生命周期"(PAR、MCP 端口占用)三类;
处理方式以"日志→根因→最小修复→实测回归"闭环,多数问题沉淀为 README FAQ 与部署检查单判据。

## 8. 总结与展望

**总结**:项目完成了"单体重构为可部署工程 → 按业务域拆分为 4 微服务 → 双流水线自动部署 → 云原生实验与性能对比"的完整闭环;过程中以工程方法(门禁、幂等、可观测、契约对齐)收敛了拆分带来的复杂性。

**展望/后续优化**(按优先级):

1. order 域引入共享会话/消息中间件前保持粘滞路由;或将验证码会话外置(Redis)进一步放开扩缩容;
2. 产品搜索改为 SQL 下推 + 分页而非内存过滤;放大 Hikari 池并加限流,改善长尾延迟;
3. 补齐单体遗留接口(用户中心订单聚合、后台 dashboard 统计)与接口鉴权缺口(admin 角色拦截);
4. 存量头像 PAR 前缀批量迁移;PAR 到期自动化提醒。
